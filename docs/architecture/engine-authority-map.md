# Engine authority map

**Status:** Active
**Last reviewed:** 2026-08-13 (schema-v9 custody subjects, offline upgrade, and S2 manual market tracer)
**Pairs with:** `docs/math-sources-of-truth.md` (concept-level registry), `docs/architecture/numerical-authority-migration-plan.md` (migration sequencing)

This document answers exactly one question: **which engine owns which job?**

`math-sources-of-truth.md` is the *concept-level* registry — one row per math concept, with the canonical file. This document is the *engine-level* map — one row per execution path, with its declared role. The two are paired: every engine that produces user-comparable numbers must also have its outputs accounted for in the concept-level registry.

If two docs disagree, `math-sources-of-truth.md` wins for math and this doc wins for engine ownership; both should be updated in the same PR.

### Clerk S3 daemon-command boundary

The host daemon owns the durable Start, Stop, and emergency-flatten command
ledger at `app/engine/live/daemon_command_idempotency.py`. One opaque key binds
one canonical command fingerprint and one outcome. A matching duplicate replays
only for an account named in the reversible host rollout setting; shadow
accounts retain and log the first outcome. A command without a final durable
outcome is unknown and is never retried in enforced mode. The data plane only
forwards the key and renders `idempotency_replayed`. This is the canonical S3
authority for issue #1156; its primary seams are
`test_daemon_command_idempotency.py`, `test_host_daemon.py`, and
`test_live_instances.py`.

### Clerk S4 account-binding ledger migration

`binding_commands.jsonl` is now the Clerk-owned append-only command ledger for
account bindings. `instance_registry.jsonl` remains the default compatibility
reader while every new decision dual-writes both records and the parity
projector remains clean. Daemon liveness facts are retirement proposals only;
the Clerk folds them under the ledger lock before accepting RPC traffic. The
durable host-control binding RPC capability is omitted from normal bot environments and
prevents bot clients from recording binding transitions. Two temporary, independently fenced compatibility writers are
limited to direct-CLI `ACTIVE run.start` and transaction-authorized lifecycle
`RETIRED lifecycle.retire` rows; all daemon and emergency binding decisions go
through the Clerk RPC. The future ledger read switch is intentionally disabled
by default and can be reversed by removing `ACCOUNT_BINDING_LEDGER_READ_ENABLED`.
This is a correctness authority among trusted processes, not same-UID hostile
code isolation; issue #1166 owns that operating-system boundary.

### Clerk S5 account-gate and session-policy migration

`account_gate_promotion.py` resolves the *effective* authority at every Start
and durable-submit boundary. The requested Clerk proof can never take effect
from configuration alone: it needs three distinct canonical NYSE shadow
sessions with no lease-weaker comparison and a typed current-generation
`CLERK_RESTART_SMOKE` record. Missing or invalidated evidence retains the
safe Account Truth path and emits an exact operator reason/disposition.

`account_session_policy.py` owns the separate account-level live-session
verdict. Canonical calendar structure and fresh durable live-feed evidence are
different facts and both are required by default. The only future hook is the
explicit durable per-account outside-session override; no bot-local policy can
weaken either gate. `LivePortfolio.submit_pending_orders` is the common normal
submit/flatten boundary, while the Account desk exposes promotion state and
the separately selected backend-authored action/session gates verbatim. This is the canonical S5
authority for issue #1158; its primary seams are `test_account_gate_promotion.py`,
`test_account_session_policy.py`, `test_live_portfolio.py`, `test_live_engine.py`,
and `test_live_instances.py`.

### Clerk S7 lifecycle-evaluator cutover

`bot_lifecycle_evaluator.py` owns every durable bot-duty decision. Its
instance-scoped `lifecycle_dispositions.jsonl` records a prepared disposition
before a state/control write and a committed or aborted outcome afterwards;
the atomic lifecycle projection carries the last disposition id, allowing a
subsequent evaluator command to repair a crash between the two records.
This receipt protocol is bot-duty evidence, not an account or broker ledger.

The authority boundary is explicit: Clerk = account and broker effects;
lifecycle evaluator = duty, roster, and control intent; host daemon = process
actuation and observed facts. The durable `STOPPED` latch may be cleared only
by Resume. This is the canonical S7 authority for issue #1160.

### Clerk S8 account cockpit

`account_cockpit.py` is the sole author of the account page's degraded mode.
It composes immutable Clerk status with one authenticated daemon-health probe;
it does not calculate broker exposure, duty state, or account permission. On
Clerk loss with a reachable daemon it authors exactly one `fix_here` blocker:
the typed, daemon-supervised Restore Clerk flow. On daemon loss or an
unreadable daemon envelope it authors `fix_elsewhere` host guidance and no
restart action. The data plane never starts a host process directly and never
offers a second broker writer. The successful restore appends an immutable
account-event receipt before the Angular store automatically re-observes the
cockpit.

## Reading guide for future contributors

A new feature lands in this repo in roughly this order:

1. **Check `math-sources-of-truth.md`** for the concept being touched. If it has a canonical row, use it.
2. **Check this map** for which engine owns the job. If the job is owned by a specific engine, extend or call that engine — do not introduce a parallel path.
3. **If there is no concept row and no engine row,** decide *first* which engine owns the new work, then add a row to both docs in the same PR as the implementation.
4. **If you find yourself wanting to compute math in `.NET` or Angular,** stop and re-read `AGENTS.md` § Python owns all math. The exception is rare and must be documented in `math-sources-of-truth.md` with `legacy-ok` status and a parity test.

## Why this doc exists, and why it's short

`math-sources-of-truth.md` answers "where is the canonical implementation of *X*?" One row per math concept, granular, dozens of rows.

This doc answers "which engine should I extend / which engine owns this job?" One row per engine path, coarse, ~20 rows.

The two documents are deliberately at different levels of granularity. A coarse engine map plus a granular concept registry is enough metadata for one developer to make consistent decisions over time. Anything more would be ceremony.
