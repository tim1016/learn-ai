# ADR 0057 — The Recency Chart's tables, writes and reads move to the Python service without dropping a row

**Status:** Accepted 2026-09-05
**Provenance:** PRD [#1927](https://github.com/tim1016/learn-ai/issues/1927) revision 2 and its adversarial review (findings F01, F07, F08, F14, F15, all verified). Built after #1926 landed the Python-owned research tables (ADR 0055), which this decision extends to a shipped feature whose tables EF Core created.
**Decision drivers:** The Recency Chart was the one research feature that persisted through .NET — a POST per run into `RecencyApi`, four EF entities, a GraphQL read — inside a sweep that is otherwise Python end to end. With .NET being deprecated that path is debt, and it had a real cost: an HTTP round-trip per cell, and a schema whose migrations cannot be generated on this host. The move must not lose evidence: Recency rows are a record of runs that happened.
**Vocabulary:** none owed — no operator-facing term is introduced; "launch", "run", "trade" and "membership" keep the meanings the Recency Chart design spec gave them.
**Related:** ADR 0055 (Python-owned research tables; `research_schema_migrations`, the writer loop, the connection helper), ADR 0049 (direct asyncpg access to an EF-owned catalog — the precedent for *access*, which this decision turns into *ownership* for these four tables).

## Decision

1. **Ownership moves whole, not piecemeal.** Every read and write the review inventoried moves to Python in one change: launch creation before dispatch (was `JobsApi`), snapshot persistence (was `RecencyApi` + `RecencyPersistenceService`), launch terminal status incl. cancellation (was `JobsApi` and `RecencyLaunchService`), the chart and hero reads (was `RecencyQuery` + the `RecencyHeroClient` round-trip back to Python), and the four soft-delete / restore verbs (was `RecencyMutation`). `JobsApi`'s `recency_chart` row stays as transport only. The one cross-feature dependency, the study hard-delete guard in `StudiesApi`, stays where its caller is and reads the table **by name** through a raw scalar query — the single permitted cross-owner read, exactly as the catalog precedent allows.
2. **The tables are adopted, not recreated.** `research/persistence/schema.py` version 3 declares the four tables with the names, columns, identity columns, indexes and constraints EF created, every statement `IF NOT EXISTS`. On an upgraded database the version is recorded and nothing else changes; on a fresh Python-only database the same shape is created. Verified on a scratch database: 35 columns, 14 indexes and 8 constraints identical between the EF-created and Python-created tables.
3. **The EF migration that removes the entities is a documented no-op.** The entities leave `AppDbContext`; `dotnet ef migrations add TransferRecencyTablesToPython` (run with the EF CLI inside the backend container) scaffolded four `DropTable` operations and regenerated the model snapshot. The operations were removed from `Up()` and `Down()` — the snapshot was **not** hand-edited — so the generated SQL for this migration is one `__EFMigrationsHistory` insert and later migrations see no Recency table to drop. Verified: the migration's SQL script contains no `DROP`; applying it to a populated scratch database left rows, sequences, foreign keys and indexes intact; `Down` is a no-op because the tables were never dropped.
4. **Writes go through the shared writer loop.** Worker threads persist with `run_sync(with_connection(repo.persist_snapshot, snapshot))` on the process-wide loop and pool from ADR 0055; FastAPI reads use its own loop's pool. Eight concurrent cells persist on one bounded pool.
5. **Redelivery is answered by identity.** Inside the launch-row lock, a snapshot whose `(launch, symbol, strategy, params_hash)` the launch already holds returns the existing run and counts nothing; a different cell in the same launch is a new execution. This replaces the old "each call creates a fresh run" behaviour the review flagged, and is what makes the cutover's unknown-commit case safe to relaunch.
6. **Read semantics are preserved, not re-derived.** Trades overlapping the window with a live membership; the representative is the newest live run (created-at, then id) matching the filters; a trade whose owning run was deleted stays visible while another live run vouches for it; the hero reads trades that *entered* inside the window; numbers cross the wire as JSON numbers, never Decimal strings. The Angular page keeps its model and gets an explicit DTO adapter.

## Cutover protocol (coordinated drain)

Both services deploy from one commit; Python's jobs run in-process, so an in-flight sweep does not survive a restart regardless of this change. The drain is therefore short and operational:

1. **Stop starting Recency sweeps.** `GET /api/jobs?active=true` must show no `recency_chart` job; wait for any running one to finish (its launch reaches `COMPLETED`, `FAILED` or `CANCELLED` through the old path).
2. **Deploy.** Backend startup applies `TransferRecencyTablesToPython` (history row only). Python's first database use records schema version 3.
3. **Unknown commit outcome.** If a worker was killed between persisting a cell and acknowledging it, the launch stays `RUNNING` with whatever it had counted. Relaunch: the new launch is a new execution (new launch id); the old launch is evidence of an interrupted run and can be soft-deleted from the page. Within one launch a redelivered cell is recognised (decision 5), so a Finish-style retry never double-counts.
4. **Rollback.** Reverting the deploy re-registers the .NET writers; `Down` is a no-op and the tables are untouched, so rows written by Python in between remain readable by .NET (same shape). Rows written by both sides in one window cannot happen because the drain forbids it.

## Consequences

- `RecencyApi`, `RecencyQuery`, `RecencyMutation`, `RecencyTypes`, the three services and their interfaces, the two DTOs, the four entities, their `AppDbContext` mappings and the GraphQL registrations are gone; the GraphQL schema snapshot shrinks by the Recency types; `contracts/openapi` gains the `/api/research/recency/*` reads and verbs.
- `persist_client.py` and its test are gone; `tests/research/recency/test_repository.py` and `tests/routers/test_recency_endpoints.py` pin the semantics above against the ephemeral database; the studies-guard test becomes a PostgreSQL integration test seeded through SQL.
- A future schema change to these tables is a new numbered statement list in `schema.py`, never an EF migration.
