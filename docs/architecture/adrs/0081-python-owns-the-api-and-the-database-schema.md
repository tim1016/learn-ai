# ADR 0081 — Python owns the API and the database schema; the C# backend is retired

**Status:** Accepted 2026-10-21
**Provenance:** Owner decision, 2026-10-21, answering four scoping questions: screens talk to Python's existing API (not GraphQL); Python manages the database with plain SQL files; the C# scheduled jobs are kept as an unused reference with a note on where they could plug in; the rollout is one switch. Built as one change on `chore/remove-csharp-backend`.
**Decision drivers:** By this date the .NET backend did three things no other component did, and each was already a thin layer over Python. GraphQL forwarded seven of its sixteen operations verbatim to Python routes and cached or stored the rest in tables only it read; `/api/jobs` minted a job id and wrote Redis keys that Python already owned; EF Core created a schema Python already queried through asyncpg. Its build could not run on the owner's machine (no `dotnet`), its container needed JIT-only flags to compile on Apple Silicon, and every cross-stack change paid for a second contract (GraphQL schema snapshot) beside the OpenAPI one.
**Vocabulary:** none owed.
**Related:** ADR 0031 (cross-stack boundary — its GraphQL and .NET rows are superseded here), ADR 0049 (lake catalog — its "EF-owned" schema is now this decision's SQL), ADR 0055, 0057, 0058 (Python-owned tables — the EF wording is superseded), ADR 0065, 0074, 0077 (they say .NET mints job ids), ADR 0071 (decision 6 names a .NET cron).

## Decision

1. **Python owns the API.** The Angular app calls Python's REST routes under `/api` through the dev proxy; the generated OpenAPI types (`Frontend/src/app/api/broker.types.ts`) are the wire types. `Backend/`, `Backend.Tests/`, `podman.sln`, the `my-backend` container, the `backend` fleet overlay and every .NET CI job are gone. GraphQL is retired: there is no schema snapshot and no `/graphql` route.
2. **Python owns the Postgres schema through plain ordered SQL files.** `PythonDataService/app/db_schema/migrations/NNNN_name.sql` are applied in filename order by `app/db_schema/runner.py`, each in one transaction, and recorded in `schema_migrations` with a SHA-256 checksum. The numbering must run 0001.. without gaps; an applied file that is edited, or a ledger row with no file, stops the run. A session advisory lock serialises concurrent runs. There is no down step and no library: asyncpg, already a dependency, runs the files. The data plane (`combined` and `fleet_coordinator` roles) runs the runner at startup before its listener opens and refuses to start if it cannot; `python -m app.db_schema` runs it for CI and for preparing a throwaway database. A clerk agent's database role is read-only and never migrates. The research tables keep their own ledger (`research_schema_migrations`, ADR 0055); this decision does not move them.
3. **`0001_baseline.sql` stands for the 36 EF Core migrations.** It was produced by running `dotnet ef migrations script` into a throwaway Postgres 16 and reading the result back with `pg_dump --schema-only`; a database built from the file dumps byte-identical to the EF-built one (23 tables beside EF's history table, no functions, triggers, extensions or enum types). The only edit to the dump is writing eight `col IN (...)` list expressions back the way the migrations wrote them, because Postgres re-parses its own deparsed form into a different, equivalent tree. A database EF already migrated is *adopted*: the baseline is recorded as applied and not run. Adoption requires the EF history table to hold `20261001045334_DropUnwrittenMarketDataTables`; a database left earlier in the chain, or one with the lake catalog table but no EF history, is refused with the remedy rather than guessed at. `__EFMigrationsHistory` is left in place.
4. **No table is dropped.** The baseline keeps every table EF created, used or not: the ledger tables (`Accounts`, `Orders`, `Positions`, ... — money trails stay), the `clerk_transaction_*` tables, `Tickers`, `StockAggregates`, and the two research-experiment tables the screens still read. A table that nothing writes is a candidate for a later numbered migration, decided on its own.
5. **`/api/jobs` is now Python's.** The public jobs facade (start by type, SSE events with `Last-Event-ID` resume, result, download, cancel, list active) moved from `Backend/Jobs/JobsApi.cs` to `app/routers/jobs_facade.py` and `app/jobs/facade.py`, one-to-one: the same paths, the same Redis keys (ADR 0065), the same control-secret header only for `data_lake_backfill` and `options_golden_search_history`, and, as before, no authentication of its own. It dispatches to the existing `/api/jobs-internal/*` routes in-process. "The API mints job ids" replaces ".NET mints job ids" wherever the ADRs say so.
6. **The sixteen GraphQL operations became REST.** Seven forwarded to Python routes that already existed and now are called directly. Data Lab sessions (six operations) and the three research-experiment reads gained Python routers (`/api/data-lab/sessions`, `/api/research/experiments`, `/api/research/signal-experiments`); their instants are `int64 ms UTC`, not ISO strings (the saved from/to dates stay `YYYY-MM-DD` form state, ADR 0022 amendment (f)). One behaviour was dropped on purpose: the Postgres cache in front of `/api/aggregates/fetch` (and its `forceRefresh` flag) — the strategy builder's daily contract history now reads Polygon through Python every time.
7. **The scheduled jobs are kept, unused.** The IV recorder cron (Quartz) and `Backend/Temporal/UnixMs.cs` live in `references/csharp-jobs/` with a README naming where a Python clock could plug in. The Python endpoint the cron called (`/api/iv-recorder/snapshot`) stays; the cron was disabled by default and never enabled in this stack, so nothing that ran has stopped. ADR 0071 decision 6 (".NET owns the cron") is superseded: nothing owns it today.

## Consequences

- CI loses three jobs (`Backend Lint`, `Backend Tests`, `Backend GraphQL Contract`) and the daily run loses `Backend Full Suite`; the daily Python job migrates its Postgres with `python -m app.db_schema` instead of `dotnet ef database update`. Pull-request CI still has no Postgres, so the SQL runner's database tests run in the daily run, as the other Postgres-gated tests do.
- The fleet topology snapshot drops `backend`; the Postgres connection inventory (`app/research/benchmark.py`) no longer reserves the backend's 100-connection Npgsql pool, which makes its free-connection verdict less pessimistic, never more.
- `python-service` now waits for `db` to be healthy, because it migrates at startup.
- A database created fresh by the runner has no EF history, so it cannot be opened by an older C# release; rolling back past this change means restoring a backup taken before it. A database adopted from EF keeps its history and can.
- CodeQL is GitHub's default setup, not a file in the repo; it stops analysing C# on its own.
- A future schema change is a new numbered file. If it changes a column or constraint of `DataLakeArtifacts`, `app/data_lake/catalog_schema.py` changes in the same pull request (the drift test fails otherwise).
- Deferred: the research tables' own ledger could move to numbered SQL files; the unused market-data tables could be dropped; `/api/jobs` could require the data-plane control secret for its two protected types instead of attaching it on the caller's behalf.
