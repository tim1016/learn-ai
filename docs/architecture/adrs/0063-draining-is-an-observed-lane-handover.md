# ADR 0063 — Draining is an observed lane handover, and order-quiet is not observable yet

**Status:** Accepted 2026-09-15
**Provenance:** Stream C of the fleet lane visibility and handover plan (`docs/superpowers/plans/2026-09-15-fleet-lane-visibility-and-handover.md`), task C1, revised after adversarial review returned SPEC FAIL / DESIGN FAIL against the first draft. The defect it closes was found by reading the fleet spine delivered under ADR 0062: `draining` is read by the router (`PythonDataService/app/broker/fleet/service.py:1269-1274`) and referenced by the registry-backup manifest's comment (`PythonDataService/app/broker/fleet/recovery.py:196-199`), admitted by the schema trigger (`PythonDataService/app/broker/fleet/schema.py:285-293`), and **written by nothing** in `app/`, `scripts/` or `tests/`. The owner resolved the lane-exit semantics on 2026-09-15: a lane leaving service stops accepting new routed work, finishes any order already in flight, and hands over — **open positions and running bots stay with the account, and draining never requires the account to be flat.** Moving infrastructure must never force a trading decision.
**Decision drivers:** The release ceremony `draining` should support gates on `RELEASE_PROOF_TOKEN` (`service.py:109`), a fixed string the operator types to swear "the old agent and volume are offline and the provider's obligations are clear" (`service.py:1052-1058`, `:1138-1144`). The string is `old-clerk-offline-and-obligations-clear`; it is defined in the same source file that checks it, exported in that module's `__all__` (`service.py:1931`), imported by the test suite (`tests/broker/fleet/test_registry_recovery.py:35`), and **printed verbatim as a copy-pasteable command line in a committed runbook** (`docs/runbooks/fleet-e-registry-recovery-exercise.md:89`). Under the owner's standing principle — *a check that cannot fire is worse than no check* — it is not a weak gate but a gate-shaped hole that makes an unproven release look ceremonious. The same principle governs the fix, and it is why this ADR's central finding is a negative one: **the fleet layer cannot observe whether an order is working, and no rearrangement of the tables it has will change that.**
**Related:** ADR 0062 (the fleet control plane this extends — Decisions 1, 3, 4, 7, 8 and addendum items 1 and 7 are applied, not amended), ADR 0047 (authority recovery is an offline ceremony against a stopped authority — the precedent for proof captured out of band by the party that can see it), ADR 0035 / ADR 0037 (the Clerk's SQLite custody authority, unchanged: nothing here moves custody between volumes), ADR 0052 (a terminal exit is operator-declared and re-verified at commit), ADR 0039 (Status is decision standing, not code conformance — load-bearing here, because this decision deliberately ships incomplete), ADR 0022 (`int64 ms UTC`).
**Vocabulary:** `CONTEXT.md` § "Broker clerk fleet (resolved 2026-09-12)" — extended with **drain**, **command quiet**, **order quiet**, **lane quiet**, **unsettled attempt** and **mount attestation**. Per ADR 0040 Decision 4.

## Context

### What the code does today

`retire_clerk` (`service.py:435-479`) moves a clerk straight from `provisioned` to `retired` and refuses only while the clerk holds an assignment that is not `released` (`service.py:447-461`). Its refusal text says "Run the host release ceremony for each assigned account, then retire" — so retirement delegates its hard question to release. Release is `release_assignment` (`service.py:1034-1111`), whose entire proof is the string equality at `service.py:1052`. `reassign_assignment` (`service.py:1114-1222`), the lane-to-lane handover, repeats it at `service.py:1138`. None is reachable over HTTP: all three are subcommands of `scripts/manage_broker_fleet.py` (`retire` `:767-770`, `release-assignment` `:772`, `reassign` `:853`), which is ADR 0062 Decision 8's host-ceremony boundary and stays that way.

The intermediate state the design implies is therefore missing. `_project_lifecycle` (`service.py:1890-1922`) will project `draining` to the directory the moment a row carries it (`:1911-1912`), and `resolve_route` will refuse every routed operation for it (`:1269-1274`). The projection and the fence were built. The transition was not.

### The central finding: order-quiet is not observable, by anything in the fleet layer

The brief's binding constraint is that a draining lane **finishes any order already in flight**. Nothing in the repository can tell whether it has.

**The routing ledger settles on the HTTP response, not on the order.** `routing_receipts` (`schema.py:218-239`) looks like an obligation ledger and is not one. `open_routing_attempt` (`service.py:1362-1436`) writes the pinned context as `not_dispatched`; `mark_routing_dispatched` (`service.py:1437-1453`) sets only `dispatched_at_ms`, leaving the state alone (`store.py:932-941`); and `settle_routing_attempt` moves the state to `delivered` **the instant the lane returns any sub-400 response** (`routing.py:485-489`). So the predicate `state = 'not_dispatched' AND dispatched_at_ms IS NOT NULL` is true for exactly one HTTP round trip — or forever, if the coordinator died mid-call. It is never true *because an order is working at the broker*. A market order accepted and still open settles the receipt to `delivered` immediately, exactly as it contributes zero to a capacity counter.

This is the same indictment this ADR levels at `_CapacityPool._inflight` below, and it applies to the receipts ledger verbatim. The first draft of this ADR made that error and is corrected here rather than defended.

**Most orders never enter the ledger at all.** The routed operation catalog holds **76 operations** (`app/broker/fleet/operation_catalog.snapshot.json`), and it is a bot and configuration control surface — `bot_admission_plan`, `bot_authority_facts`, `bot_chart_history` and their siblings. An order placed by a lane's own bot runner on its own schedule never reaches the coordinator, so no receipt exists for it. Per ADR 0062 Decision 1 the registry stores no order, fill or position data by design, and per `docs/design/fleet-d-runtime-ownership-matrix.md:22-23` runner state is lane-local. The coordinator's blindness here is architectural, not an oversight to be patched.

**Routed streams leave no trace either.** `stream_read` (`routing.py:251-320`) resolves and dispatches without ever calling `open_routing_attempt`. A lane serving an open SSE subscription is invisible to the receipts table.

**And the ledger leaks in-flight rows for reasons unrelated to orders.** `deliver_command` calls `mark_routing_dispatched` (`routing.py:422`) and then, at `routing.py:444-445`, `except FleetControlError: raise` — re-raising **without settling**. Any `FleetControlError` from the delivery path leaves a receipt permanently dispatched-and-unsettled, and nothing in the repo sweeps such rows. So the predicate is not merely blind to orders; it accumulates false positives over time.

`_CapacityPool._inflight` (`lane_runtime.py:120`, mutated `:128`, `:141`, `:149`) is no better, on four independent counts, each sufficient: it is an in-memory integer a restart zeroes, so a crashed lane reports perfect quiet; it does not exist on the coordinator, whose middleware enforces capacity "only on an agent" (`lane_runtime.py:450`, guarded at `:460-479`); it counts HTTP calls, so a working order contributes zero; and it is a count rather than a set, so the obligation cannot be named and therefore cannot be reconciled — which is the only remedy ADR 0062's addendum item 7 prescribes.

**Conclusion.** Order-quiet is observable only by the lane, which holds the broker connection and its own custody database, and **no lane-side surface exposes it today.** The fleet layer has no substitute and must not manufacture one. A gate that always passes is the defect this ADR exists to remove; relocating it into a different table would be the same failure wearing a schema.

### What the registry *can* observe

Three things, each genuinely durable, and none of them order-quiet:

- **An unsettled attempt** — `state = 'not_dispatched' AND dispatched_at_ms IS NOT NULL`. Correctly read, this means *the coordinator dispatched a command and lost its outcome*. That is a real reconciliation obligation and worth gating on, but it is bookkeeping about the coordinator's own knowledge, not about the broker.
- **Whether a clerk ever served** — `account_assignment_history` (`schema.py:406-417`) and `clerk_session_history` (`schema.py:145-153`) are append-only, written only by `append_assignment_history` (`store.py:704-738`) and `archive_session` (`:468-483`), and never pruned — each carries an immutability and a no-delete trigger (`schema.py:419-429`, `:330-340`), and no `DELETE FROM` statement exists anywhere in `store.py`. **`clerk_sessions` is equally permanent, by the schema and not by convention**: `trg_clerk_sessions_no_delete` (`schema.py:324-328`) aborts any delete with "a superseded session is archived, not deleted". A clerk with no row in either history table **and no live `clerk_sessions` row** provably never served — Decision 6 shows why that third clause is not redundant.
- **Volume and assignment identity** — unchanged from ADR 0062.

### What only the host can observe

`verify_volume_identity` (`volume.py:201-245`) proves that a root handed to it carries the expected clerk's marker. It runs co-located with its caller and is a statement about *identity*, never *occupancy*: a mounted-but-idle volume and an unmounted one are indistinguishable from the coordinator. ADR 0062 Decision 8.1 forecloses the only mechanism that would change this, because giving the data-plane service container-level authority converts any compromise of that service into a host compromise. The volume fact is irreducibly a host fact.

### The owner decision, checked against the code

**"Positions stay with the account; drain never forces a flat" is fully supported and costs nothing.** No existing gate reads exposure; the coordinator computes no positions by design. This ADR adds no gate that does.

**"Running bots stay with the account and the successor lane adopts them" is not supported today**, and Decision 8 records that rather than designing around it. Runner state is on the predecessor's volume; `write_volume_marker` refuses to overwrite an existing marker — "a clerk volume is provisioned once and never re-marked in place" (`volume.py:102-115`); `volume_id` is immutable (`trg_clerks_identity_immutable`, `schema.py:263-277`); the active-clerk unique indexes reserve it for any non-retired row (`schema.py:100-107`); and `reassign_assignment` verifies the **successor's own** root before releasing the predecessor (`service.py:1141`). No successor can mount a predecessor's volume, so none inherits runner state, ledgers or custody.

## Decision

### 1. `draining` becomes a written state with a durable start instant, and entering it is deliberately cheap

A host ceremony `drain_clerk` performs `provisioned -> draining`, requiring only that the registry recovery hold is clear (`recovery.py:400-423`) and the clerk is `provisioned`. **Nothing else gates entry.** `resolve_route` already refuses a draining clerk (`service.py:1269-1274`), so the transition *is* the stop-accepting-new-work step; a drain that could be refused for being inconvenient would leave an operator unable to close the door.

It writes **`draining_since_ms`**, a new `int64 ms UTC` column on `clerks` — the table carries only `created_at_ms` and `retired_at_ms` today (`schema.py:93-95`), so without it the bound in Decision 5 has no origin. Schema v5, with the standard `>= 0 AND <= MAX_TIMESTAMP_MS` bound (`schema.py:48-50`) and a `CHECK` requiring it non-null when `lifecycle_state = 'draining'`. This column is additive; **v5 as a whole is not**, and Consequences carries the full six-change inventory and says which change breaks the claim. It is not paired to retirement the way `retired_at_ms` is: a clerk that drained then retired keeps both.

The lane learns it is draining from the heartbeat. `observe_session` (`service.py:669-717`) returns a bare `bool`; it returns the clerk's durable lifecycle state instead. This is a read of a fact the registry already holds and grants the lane no authority, consistent with ADR 0062 addendum item 1.

**On learning it is draining, the lane is obliged to stop admitting new bot decisions and to wind down its runner.** Nothing in the current code obliges it — `observe_session` refuses only for `RETIRED` (`service.py:688-693`) — and this ADR does not add a coordinator-side enforcement, because the coordinator cannot see a runner. It is a lane-side obligation owed by each provider adapter, and it is stated here so it is designed rather than discovered.

### 2. Order-quiet is a required gate that cannot be implemented yet, and the ceremony ships saying so

`draining -> retired` requires **lane quiet**: the lane holds no working order and runs no bot decision loop, asserted by the lane about its own broker connection and custody.

It arrives as a **confirmation**, not an observation, modelled on `confirm_assignment` (`service.py:873-972`) and inheriting its fences exactly: refused unless the calling `agent_instance_id` and `routing_epoch` equal the current session's (`service.py:934-940`), compared inside the recording transaction, and additionally refused if `observed_at_ms < draining_since_ms` — quiescence observed before the door closed proves nothing about the period after it. A `reported_summary` heartbeat field (`records.py:90-150`) would be an observation and, under ADR 0062 addendum item 1, would confirm nothing; it would be worth exactly as much as the token.

**No provider can currently answer it.** `authority_state` is a bounded snake-case token with no closed vocabulary at the fleet layer (`records.py:86`, `:139-142`), and nothing in `app/broker/fleet/` can compute the predicate. The Alpaca adapter owes: a lane-local query over its own custody database and broker connection returning *no working order and no admitting bot runner*, as one bounded fact with its observation instant.

**Until that ships, `draining -> retired` does not complete.** There is no fallback, no degraded automatic path, and no operator attestation that substitutes. A drain may be entered; a lane may be **released** once §4.1's deadline has elapsed; **reassignment is unreachable altogether** for the separate reason §4.1 concludes; and retirement waits. This is the deliberate choice: an operator blocked at a gate that cannot yet be satisfied learns the truth immediately, whereas a gate that degrades to an attestation would reproduce `RELEASE_PROOF_TOKEN` in a new location and teach everyone the ceremony is a formality. The first draft of this ADR contained exactly that unconditioned degraded path; it is removed.

The one relief is Decision 5's `force-retire`, which is a **separate, named, operator-attributed ceremony** — never a fallback inside `retire`.

**Amendment (owner decision 2026-09-19, remaining details confirmed 2026-09-21, closing #2154): lane quiet is five conditions, the lane asserts them, and the operator performs the acts.** The gate above named two — no working order, no admitting bot runner. It names five now, and a lane is quiet only when all five hold together at one observed instant:

1. **The lane is draining.** It accepts no new routed work, and since #2155 it starts no new bots once it has learned its drain (`app/services/bot_runner.py`'s new-run refusal, latched by `fleet_boot._learn_drain`). Decision 1 stated this obligation and enforced nothing; without the enforcement the other three conditions would be true only for an instant, so it is a condition here rather than an assumption.
2. **No bot is running**, meaning the runner has confirmed its exit — not that the panel records the desired state `STOPPED`, which records only that the operator *wants* the bot idle and is satisfied the moment they click.
3. **Every working order on the account has ended**, meaning the broker reports a finished state — not that a cancel was requested. A cancel races a fill and a fill opens a position, so "cancel sent" is not an ending, and a gate that accepted it would pass a lane into retirement with an order still live. The scope is the **account**, read from the provider's own order list, for the same reason condition 4 reads the account: an order the lane did not place can still fill and re-open a position after the confirmation is taken, and a lane-attributed reading would be silent about exactly the order nothing in the lane can cancel. Because an account is bound to one lane at a time, the account-level answer *is* the lane-level answer and no per-order attribution is needed.
4. **The account is flat**, read from the provider's own position list for the whole account rather than from the lane's bot-attributed custody.
5. **No order intent is in flight** — every durable intent has a resolved broker outcome. This is not covered by condition 3 and the repo already keeps the two sets apart: `InstanceCustodyProof` carries `working_order_refs` and `unresolved_intent_refs` as separate tuples (`app/broker/alpaca/clerk/models.py:597`, built in `app/broker/alpaca/clerk/sqlite/runtime.py`), and `app/services/bot_carryover.py:222` already treats *either* being non-empty as an outstanding obligation. An intent whose broker identity the lane cannot yet establish is nothing at the broker to report a finished state *for*, so condition 3 cannot be evaluated for it; it is outstanding, not absent. Omitting it would reproduce condition 3's own hazard — an unresolved submission racing the gate — in the one place the gate cannot see.

The operator performs 2–4 with actions that already exist in the bot panel — `stop`, `cancel_verified_working_orders`, `flatten_stop` — in that order, waiting for the flatten's own orders to end before all five are re-read. Condition 5 is not an operator act: it clears as the lane resolves its own intents, and it refuses until it does. **The lane then proves it.** An operator click is not evidence, which is why this stays a confirmation and does not become an attestation.

**Amendment (2026-09-23, closing #2351): the drain closes the door on new work, not on the acts that make the lane quiet.** Until this amendment `resolve_route` refused *every* routed operation for a draining clerk, the three acts above included, so a lane drained with a bot running could never answer quiet from the panel. A draining clerk now routes exactly what `ProviderOperation.routable_while_draining` admits — one allow-list over the catalog's own classification: every `read` operation (the panel, the custody reads, `lane_account_quiet_read`), plus the mutations declared `quiesce` (`OperationDrainAdmission`): `lane_stop_all_bots`, `bot_panel_quiesce_action` (the panel's `stop` and `flatten_stop`, split from `bot_panel_action` because that one operation also resumes and continues bots), both custody `recovery-actions/execute` operations (whose executor only stops decisions, cancels verified working orders, flattens or reconciles) and `custody_runs_stop`. Everything that can open exposure still refuses — starts, resumes, deploys, paper access, graduation, manual orders, configuration writes, go-live release — so §7.2's "a draining lane is unroutable" now reads "unroutable for new work". `force-retire` is unchanged and stays deadline-only (Decision 5's amendment keeps it the exit for a lane "holding an obligation its operator declines to discharge"); what closes the gap it left is the lane: registration, confirmation and the heartbeat refuse a retired clerk with the typed `clerk_lane_retired` (lane side `fleet_lane_retired`, kept out of the FR-066 unavailability family), and a lane that hears it for its own clerk tombstones its evidence, stops every bot through the lane-wide stop, stops re-registering and ends its beat (`fleet_boot._learn_retirement`).

**Condition 4 does not breach §8, and §8's own amendment is where it comes from.** §8's first sentence — no gate in this ADR reads a position — stands unchanged, because it binds the *fleet layer*, which still reads no position, holds none and stores none. What crosses the seam is one bounded fact the provider computed against its own broker connection: precisely the shape §8's 2026-09-19 amendment already requires for handover, "provider-owned nothing-open evidence — Decision 2's lane-quiet shape, counting positions *and* working orders, a resting GTC included per Decision 5". Retirement and handover consume the same evidence and it is built once, which is the issue's own instruction. The registry stays custody-free: the durable record is the confirmation and its instant, and `lane_confirmation` remains `present` or `absent` — never a quantity, a symbol or an order id. A refusal names **which condition is outstanding**, not its contents, for the same reason.

**Requiring the account flat here does not reopen the 2026-09-15 decision, and the anti-pattern it appears to contradict is narrowed rather than dropped.** Drain entry and release stay flat-free and are untouched: a lane may stop serving, wait out the deadline and be released while positioned, and the account then sits unassigned with its positions at the broker for as long as the operator chooses. What condition 4 gates is **retirement on the normal path, and nothing else**. No ceremony forces a trading decision, because `force-retire` stays reachable for a positioned lane on its own deadline. **The normal path is not *faster*** — an earlier revision of this paragraph claimed it was, and that was wrong: `retire_clerk` requires every assignment released first, and §4.1 makes release wait out the same `drain_deadline_at_ms` that bounds `force-retire`, so both paths serve the same wait. What flattening buys is what the retirement *is*: a lane that confirms retires with `lane_confirmation: present` on the unforced path, leaving no forced-unknown correlations to reconcile by identity afterwards and not adding to the auditable forced count. The deadline is not waived to deliver that, and #2154's implementation must not waive it. "Moving infrastructure must never force a trading decision" survives intact; what changes is that flattening now buys something — standing, not speed.

**Silence is never quiet, and the direction of that rule is what makes it safe.** The confirmation inherits `confirm_assignment`'s fences exactly — the calling `agent_instance_id` and `routing_epoch` must equal the current session's, compared inside the recording transaction — plus this ADR's own `observed_at_ms >= draining_since_ms`. **The instant is bounded above as well as below**: the lane supplies it, so a confirmation stamped after the coordinator's own `now` is refused outright rather than admitted with a negative age — one whose clock ran ahead, or which sent `MAX_TIMESTAMP_MS`, would otherwise never age out of `lane_quiet_valid_for_ms` and would hide every order and position created after the real observation. **Nor does the instant order or identify a confirmation.** The evidence table is keyed and read on the registry's own append sequence, because a lane host whose clock stepped back would otherwise choose which of its own answers the gate reads, and could retire itself on a quiet claim it had already withdrawn. The instant is kept for freshness alone — and a backward-stepped clock then makes evidence look *older*, which refuses sooner. Two further rules follow from the five conditions being a *state* rather than an event: a confirmation does not survive the session that made it, because conditions 2, 3 and 5 are claims about a running process's own knowledge and a restart destroys that knowledge; and a confirmation the lane has stopped re-asserting goes stale, at which point the gate refuses. **The staleness bound is the confirmation's own, not the session's.** The gate compares `now` against the confirmation's `observed_at_ms` and refuses past `lane_quiet_valid_for_ms` — an `int64 ms UTC` deployment value sized as a small multiple of the lane's confirmation-push interval, and derived from **that** interval, never from `DEFAULT_SESSION_STALE_AFTER_MS` (`service.py:100`), which Decision 5 already forbids reasoning from for the deadline and forbids here for the same reason: it measures heartbeat-detection latency, a different quantity. The distinction is what keeps this clear of Decision 5's prohibition — a live session that has stopped confirming refuses exactly as a dead one does, so what refuses is the **evidence** being old, not the lane being quiet-by-silence. Liveness is neither necessary nor sufficient here and is never read. **This is not the staleness Decision 5 forbids.** Decision 5 forbids heartbeat silence from *moving* something — releasing, transferring or retiring on its own. Here silence makes a gate **refuse**, which is the opposite direction and the one this ADR takes everywhere else: an unreachable lane proves nothing, so it passes nothing. Re-assertion is a repeated confirmation, not a heartbeat field; the objection at the head of this decision — that an observation confirms nothing under ADR 0062 addendum item 1 — applies to a periodic observation exactly as it applied to a single one.

**A lane that restarts mid-drain never confirms, and that is the intended trade.** The fence above says a confirmation does not survive the session that made it; #2155 makes the consequence sharper than "re-confirm from the new session", because there is no new session to confirm from — `register_agent_session` refuses a draining clerk outright, so a drained lane never returns to service. A lane whose process dies during its drain therefore cannot answer at all, and `force-retire` is its exit. That is the correct side to err on: letting it re-register in order to confirm would reopen exactly the resurrection hole §7.1's amendment closed, and a lane that lost its process has also lost the running-process knowledge conditions 2, 3 and 5 assert. The cost is real and is stated rather than discovered: a drain is long, so a restart inside it is not exotic, and every such lane is a forced retirement that the count in Consequences will keep showing.

**Residual, named rather than hidden:** the confirmation is a point-in-time fact and retirement consumes it a moment later. A drained lane admits no new bot and so originates no new algorithmic order, but an operator acting through the panel's manual-order surface inside that window can make the lane un-quiet after it said otherwise. The only bound is that the same operator is running the ceremony. No coordinator-side interlock closes it and none is added here; naming it is what this ADR owes, and it is strictly narrower than the hole `force-retire` covers today.

### 3. Command quiet is a real but narrow gate, and it is not the order gate

`draining -> retired` additionally requires zero unsettled attempts for the clerk (`state = 'not_dispatched' AND dispatched_at_ms IS NOT NULL`), plus the pre-existing no-unreleased-assignment check (`service.py:447-461`).

This is retained at its true strength and no higher: **it prevents retiring a lane past a command whose outcome the coordinator lost.** On a healthy lane it is satisfied immediately and blocks nothing, which is correct — it is not measuring orders and never claimed to. It needs a supporting partial index on `(clerk_id)` over that predicate; the existing indexes (`schema.py:245-254`) serve the audit read's ordering.

Two honest limits ride with it. The routing.py:444 leak means it can be false for reasons having nothing to do with orders, so the leak is a prerequisite fix, not a nice-to-have: the `except FleetControlError` branch must settle `outcome_unknown` before re-raising, as its two sibling handlers do. And routed SSE streams open no receipt at all (`routing.py:251-320`), so an open subscription is invisible to it — either streams gain an attempt row, or the gate's scope is documented as commands only. This ADR requires the former if streams are ever to be part of drain evidence, and accepts the latter meanwhile.

**Claim withdrawn from the first draft:** that computing this inside the lifecycle transaction closes the race. It does not, on its own — `open_routing_attempt` (`service.py:1362-1436`) performs no lifecycle check, and the ceremony runs in a separate host process from the coordinator serving traffic. But the lifecycle *is* checked immediately before it: `_resolve` (`routing.py:500-528`) calls `resolve_route` before `open_routing_attempt` on every command path, and `resolve_route` already refuses a draining clerk (`service.py:1269-1274`). What remains is a narrow time-of-check/time-of-use window between resolve and dispatch — not an unchecked lifecycle — and the pinned `routing_epoch` and `agent_instance_id` `open_routing_attempt` already records (`routing.py:387-402`) fence a session change across that window even without a second lifecycle read.

### 4. What replaces `RELEASE_PROOF_TOKEN`, and the one attestation that survives

The token is deleted from `service.py:109`, `__all__` (`:1931`), both call sites (`:1052`, `:1138`), the `--proof` flag, the tests and the runbook line.

`RELEASE_PROOF_TOKEN`'s own docstring (`service.py:102-109`) bundles **four** claims, not three: the old agent is offline, the old volume is offline, credentials are isolated, and the provider's obligations are clear. Naming a home for each, honestly, rather than rounding the count down and leaving the mapping implicit:

- **The old volume is offline** survives as the operator's mount attestation below — the host alone can observe its own mounts, and ADR 0062 Decision 8.1 deliberately denies the coordinator the authority to look.
- **The provider's obligations are clear** is a claim about the broker, so its only honest home is Decision 2's lane quiet — the one gate that speaks to the broker connection at all. It is **not** Decision 3: command quiet proves only that the coordinator lost no dispatch outcome, and this ADR's own central finding is that this says nothing about the broker. Decision 2 is unimplemented today, so no proof of this claim lives anywhere yet — it is homed, not satisfied.
- **The old agent is offline** and **credentials are isolated** are both unhomed. Nothing in this ADR observes process liveness — Decision 5 forbids heartbeat staleness from gating anything, on ADR 0062 Decision 4's grounds — and nothing here inherits the credentials claim; it is a host fact exactly like the volume claim, but the attestation below names only the volume. Naming these two as unhomed is the finding this accounting owes; dropping them silently would be the token's own failure repeated in a new document.

It is recorded in the shape `closeout_empty_registry_recovery` already uses for the one comparable irreversible host act (`recovery.py:426-473`): bounded `operator` (≤128) and `change_ref` (≤512), non-empty, with the attestation instant. This buys **attribution, not proof** — a change reference is unique per ceremony and names who acted and why; a phrase published in the repository that checks it is replayable and names nobody. **Both `release_assignment` and `reassign_assignment` record their own attestation independently**, exactly as each independently checked the deleted token at its own call site (`:1052`, `:1138`) — one `operator`/`change_ref` per ceremony invocation, not one per account or per clerk.

**Both `release_assignment` and `reassign_assignment` require the clerk to be `draining`, command-quiet, and past the drain deadline** — the same two-legged, calendar-derived instant Decision 5 defines and gates `force-retire` on, not a bare `draining_since_ms + drain_deadline_ms` sum. The first draft gave the draining/command-quiet precondition to reassign only, leaving release able to consume the gate without the closed door that makes it meaningful; they are symmetric now. Neither draft gave either ceremony a wait tied to order-quiet's own bound — §4.1 states why that gap is a real hazard and closes it this way rather than leaving it open. This precondition is also what makes **reassignment** unreachable today, for the reason §4.1 draws out: it requires a draining predecessor, and §7.1 forbids reassignment against a drained lane.

### 4.1 The two-writer hazard on release and reassign, named explicitly

Handover is strictly more dangerous than retirement: retirement only stops writes, handover starts a new writer while the predecessor's order-quiet was never established. §7.1 names exactly this hazard for the FR-066 restart case — a predecessor's lane-local runner still placing orders while a second party gains write rights to the same account — and until this revision it went unnamed on the path that most resembles it.

`release_assignment` and `reassign_assignment` proceed on door-closed (`draining`) plus command-quiet plus the mount attestation, with **zero evidence about the predecessor's working orders** — Decision 2's lane quiet is unimplemented, exactly as it is for retirement. (For reassign this is stated as the precondition set the implementation must build; the divergence below explains why the ceremony does not actually run today. The hazard is not hypothetical for that reason — the last paragraph of this section shows it is reachable without reassign at all.) Unlike retirement's normal path, the preceding draft's release/reassign preconditions carried no time cost at all: a lane could be drained and reassigned in the same breath, with no wait analogous to `force-retire`'s deadline.

This revision applies the ADR's own proof to handover rather than special-casing it around the gate that makes retirement honest: release and reassignment now require Decision 5's deadline instant to have actually elapsed — both its legs, exactly as `force-retire` requires — and each records `lane_confirmation: absent` as a durable fact on the transition, so an auditor can count how many handovers proceeded without it — today, all of them.

**Release and reassign diverge here, and the divergence is a conclusion rather than an oversight.** The deadline does **not** block *release* outright: `retire_clerk` refuses while assignments are unreleased (`service.py:452-461`), so an unconditional block on release would block every exit from the fleet. For release the deadline bounds the wait, on the same basis this ADR already uses for the symmetric retirement problem, and **release remains available** — drain, wait, release, `force-retire` is a complete, reachable exit path.

**For *reassign*, the same precondition combines with §7.1 to make the ceremony unreachable, and this ADR states that as its conclusion rather than resolving it.** Reassignment now requires a predecessor that is `draining`; §7.1 establishes that reassignment must not be performed against **any** drained lane, because `fleet_boot.py:284-300` takes the offline path on any `FleetPresenceError` and boots the last-effective binding from the evidence file alone (`:385-404`), while `register_agent_session` refuses only `RETIRED` (`service.py:571-572`) and never `DRAINING` — so a drained lane really can resurrect its binding by restarting during an outage. The two constraints are each independently correct and jointly exhaustive: **reassignment is blocked outright until #2155 closes.** There is no legal predecessor state, and no wait discharges it.

Blocking it costs little, and that is why it is accepted rather than engineered around. The owner has already decided that lane-to-lane reassignment is the path nobody should take: whole-machine migration is the preferred route (#2151), which moves each lane's volume with its lane and needs no successor to inherit anything, and #2150 records the lane-to-lane adoption hole as largely avoided by that route. §8's independent prohibition — no reassignment against an account with open positions — already narrowed the ceremony to near-nothing. What §4.1 and §7.1 jointly add is that the remaining sliver is closed too, on a *different* ground, and reopens only when #2155's offline-recovery indistinguishability is closed. Reassignment is not an exit from the fleet; release is, and release is unaffected. The block is a fact about one ceremony's reachability, **not** a safety property — the open hole below shows the same two-writer shape is still reachable without it.

**Amendment (2026-09-21, closing #2155): the block above stands on moved ground.** §7.1's resurrection mechanism — the general case this section leaned on — is closed for every lane that learns its drain (heartbeat lifecycle answers, typed registration refusal, evidence v2 tombstones; §7.1's amendment has the inventory). What keeps the block in force is the *residual window* §7.1 now names — a lane unreachable for the entire drain holds unmarked evidence and remains indistinguishable from a quiet one — plus the still-missing lane-quiet confirmation (#2154). **Reassignment is blocked outright until #2154 closes**, on the same jointly-exhaustive shape: no legal predecessor state, no wait discharges it, and whole-machine migration (#2151) remains the preferred move.

**Open hole, not closed by this revision:** the deadline bounds the wait but proves nothing about the predecessor's orders during it, exactly as it proves nothing for `force-retire`. The successor-side mitigation — the successor's runner refusing to admit decisions until it has independent evidence the predecessor is quiet — does not exist, has no owner, and is not among the prerequisite fixes in Consequences. Blast radius: a handover that proceeds at or after the deadline against a predecessor whose bot runner never actually wound down (Decision 1 states that obligation but does not enforce it) hands write rights to a successor while the predecessor may still be working an order — two writers against one account. Decision 1's lane-side wind-down obligation is the intended closure and remains unenforced; this hole persists until it, or an equivalent successor-side check, ships.

**Amendment (2026-09-21, #2154): the hole now has an owner, and it is not a separate build.** Two things moved. Decision 1's wind-down obligation is enforced as of #2155 — a lane that learns its drain starts no new bots (`app/services/bot_runner.py::drained_lane_start_gate`) — which narrows the hazard to a bot already running at drain time rather than any bot at all. And the "independent evidence the predecessor is quiet" this section says nobody owns **is Decision 2's lane-quiet confirmation**. The closure is therefore not the successor-side runner convention this paragraph imagined, but something stronger and already inventoried: the handover ceremonies consuming that confirmation, which Consequences lists under #2154 as items 5–7 — `release_assignment` recording `present` when a confirmation covers the release instead of hard-coding `absent`, `reserve_assignment`'s released branch consuming it, and `reassign_assignment`'s transfer arriving behind the same gate. A coordinator-side refusal is a gate rather than a convention, so it binds a successor that never implemented the check. **The hole closes with #2154 if and only if the confirmation is wired into those three paths and not only into `retire`** — wiring it to retirement alone would close the gate this ADR opened and leave the one it named open.

**And blocking `reassign_assignment` does not close it, which is why the hole is stated against release too.** The two-writer shape is reachable in two steps without the reassign ceremony: `release_assignment` frees the key, and `reserve_assignment` explicitly reuses a released assignment — "a fresh reservation at a higher generation" (`service.py:824-838`) — for any *provisioned* clerk (`:768-772`). Release-then-reserve is therefore the live path to a second writer today, and it carries only release's own preconditions: draining predecessor, command quiet, the mount attestation, the elapsed deadline, and `lane_confirmation: absent` recorded. That is strictly less evidence than `reassign_assignment` would gather, because `reserve_assignment` verifies the successor's volume root only when its caller supplies one (`service.py:783-784`) while `reassign_assignment` verifies unconditionally (`service.py:1144`). The gap is narrower than "never": a successor booting through `LocalPresence` does supply a root — it is a required constructor argument, and its docstring says so (`presence.py:128-140`). The callers that skip the check are `RemotePresence`, which supplies none by design because the coordinator never inspects an agent-local path, and the whole-machine migration's direct service call (`manage_broker_fleet.py:563`), which passes no root. There is no operator-facing `reserve-assignment` verb at all, so step 2 of this path is normally taken by the successor lane's own boot rather than by an operator hand — which is what makes it easy to reach without noticing. One further check is also skipped: `reassign_assignment` refuses a successor that already holds an active assignment, `reserve_assignment` does not, and `ix_account_assignments_owner` is a non-unique index, so the schema does not backstop it either. That widens the hole without changing the hazard it names. Naming reassignment as blocked while leaving this unsaid would claim a safety this ADR does not deliver.

This is precisely the shape the Anti-patterns list rejects as "leaving a ceremony optional by preserving an unenforced direct path around it." It is **inherited, not introduced** — `reserve_assignment`'s released-key reuse predates this ADR and serves the legitimate re-reservation case — and this ADR does not close it. Closing it means either refusing a reservation of a key released from a lane that never gave lane quiet, or gating the *successor's* confirmation on evidence the predecessor is quiet, which is the same successor-side mitigation the hole above already names as ownerless. Recording it here is the minimum owed; it is not fixed.

**Amendment (2026-09-22, closing #2157): the two-step reach now carries the ceremony's gate — one gate, not two policies.** `reserve_assignment`'s released-row branch no longer reuses. Reserving a released assignment *is* a clerk-to-clerk transfer wearing a reservation's clothes, and it refuses on exactly the ground `reassign_assignment` refuses on: the typed `ClerkReassignmentBlocked` naming #2154's missing lane-quiet confirmation. The branch also takes the two proofs the hole above showed it skipped: the successor's `volume_root` is **required** — "the coordinator may not have the volume mounted" is a reason to refuse a transfer, not to skip its proof, so the remote shape (`RemotePresence`, which cannot carry a volume proof) never moves a released account — and the released row's holder is re-read inside the write transaction, where a draining or retired predecessor is the release ceremony's own aftermath while a provisioned or absent holder is registry inconsistency reported rather than repaired. A retired predecessor is deliberately accepted here: drain → release → `force-retire` is the runbook's normal exit, so a released row under a retired lane is the expected end state, not corruption. Whatever one day opens the reassignment ceremony (#2154's lane-quiet confirmation) opens this branch with it, and nothing else does; the successor-holds-no-active-assignment check the hole above noted as missing is subsumed — the branch refuses entirely, so no successor acquires anything.

The honest consequence, stated rather than hidden: **an account whose assignment is RELEASED cannot be reserved by any lane until #2154 ships.** Re-onboarding a retired lane's account onto a new lane waits for the lane-quiet confirmation, on the same ground the direct ceremony waits. Whole-machine migration is unaffected — the lane keeps its identity and its assignment stays effective under the same clerk, so nothing is released and nothing transfers. And the wider hole above — the two-writer shape during any handover that does proceed, including the successor-side mitigation that still does not exist — is untouched by this amendment; #2157 closed the *less-evidenced route*, not the hazard itself.

### 5. A stalled drain is bounded by a deadline and discharged by a named ceremony, never by a fallback

A drain stalls when an unsettled attempt never settles, or when the lane never confirms quiescence because it died.

The bound is an absolute deadline instant, `int64 ms UTC`, computed from `draining_since_ms` at drain time — the deployment-owned duration is one of its two legs and the trading calendar supplies the other, per the floor below. Before it, retirement refuses and names what is outstanding. At or after it, one additional **separately named ceremony**, `force-retire`, becomes available, and it:

- requires the deadline to have actually elapsed;
- settles each still-unsettled attempt as `outcome_unknown` via `settle_routing_attempt` (`service.py:1455`), which fabricates nothing — that value *means* "may have executed, reconcile by identity, never resubmit" (`records.py:62-75`);
- records, as first-class durable facts on the retirement, `lane_confirmation: absent` and every forced correlation id;
- carries its own `operator` / `change_ref`.

It is a distinct CLI verb, not a branch inside `retire`, so that an operator who force-retires knows they did and an auditor can count how often it happens. **There is no background reaper**: the deadline gives the bound, the operator gives the act, on ADR 0047's grounds.

**The deadline has a two-legged floor, and the second leg is the calendar's, not a wall clock's.** The effective deadline instant is

```
max( draining_since_ms + drain_deadline_ms ,
     session_close_ms_utc( first session whose open is at or after draining_since_ms ) )
```

with `drain_deadline_ms` itself not less than 24 hours (`86_400_000` ms), and every value `int64 ms UTC`. The duration must be justified against a plausible working-order lifetime, not against `DEFAULT_SESSION_STALE_AFTER_MS` (`service.py:100`) — that 30-second module constant measures heartbeat-staleness detection latency, an entirely different quantity, and the 24-hour floor is 2,880 times larger.

The calendar leg is what makes the claim true, and the first draft's flat 24 hours did not carry it. A regular-hours DAY order still open at drain time is force-expired by the exchange no later than that session's close, so the honest floor is *a session close the lane can actually reach* — and 24 wall-clock hours does not guarantee one. Drain at 15:55 ET and a flat 24h buys five minutes of the session it was entered in; drain Wednesday at 15:55 ahead of a Thursday holiday and the entire remaining 24h is non-trading time. The inference "24h spans a full regular session plus its close, therefore a winding-down lane has a full trading day" is false, and it was reasoning a session boundary out of a wall-clock constant — which `.claude/rules/temporal-rigor.md` bans outright: scheduled session structure derives from the canonical calendar module, and a hardcoded duration standing in for a session boundary silently mishandles early closes and long weekends.

The repo already exposes the instrument. `PythonDataService/app/lean_sidecar/trading_calendar.py` provides `next_trading_day` (`:120`), `session_open_ms_utc` (`:143`), `session_close_ms_utc` (`:165`), `is_early_close` (`:103`) and `session_state_at_ms` (`:315`), all returning `date` or `int64 ms UTC`. The second leg is computed from them at drain time, and the resolved `max(...)` above is stored as an absolute instant on the clerk row — `drain_deadline_at_ms`, Consequences change 7 — consistent with §7.1's "the deadline is an absolute instant rather than a countdown". Across a half-day close the leg resolves to that day's actual early close rather than a 16:00 literal; across a long weekend it resolves past it. A deployment may set `drain_deadline_ms` higher; it is a floor, not a default, and a deployment setting it at or near the floor should expect `force-retire` to fire on any lane whose working orders routinely outlast one session.

**The GTC case is reconciled rather than carved out, and it has a permanent consequence.** An earlier revision excused a resting GTC order as "a position concern, not an in-flight-order one." That is false on this ADR's own definitions: Decision 2 requires the lane to hold **no working order**, `CONTEXT.md` defines order quiet as no order placed by or through the lane still working at the broker, and `TimeInForce.GTC` (`app/broker/contract/models.py:54-61` — "good-til-canceled"; permitted with `extended_hours` at `:115`) is a real, reachable, *working* order that is not a position. The account-flat clause does not reach it: "drain never requires the account flat" is about exposure, and a resting limit order is not exposure.

So the consequence is drawn rather than dodged: **a lane holding a resting GTC cannot satisfy lane quiet, and cannot satisfy it even after #2154 closes — it is permanently force-retire-only.** No deadline discharges this; a GTC rests indefinitely by definition, so both legs of the floor elapse with the order still working. The alternative — scoping lane quiet to exclude resting GTC — is rejected on this ADR's central grounds: it would weaken the one gate that speaks to the broker connection at all into a gate that passes while a real obligation is outstanding, which is `RELEASE_PROOF_TOKEN`'s failure in a new place, and it would make `CONTEXT.md`'s order-quiet definition untrue as written. The cost of accepting instead is bounded and already designed for: `force-retire` is deadline-conditioned, separately named, operator-attributed and audited, and it is already the only retirement path for a served clerk today. Crucially it preserves the owner's decision — the operator is **not** required to cancel the resting order to retire the lane, because cancelling it would be a trading decision, and `force-retire` is exactly the exit that does not demand one.

**Amendment (owner decision 2026-09-19, closing #2154): the GTC carve-out is reversed, and `force-retire` is recast as the exit for a lane that cannot answer.** The paragraph above concluded that a lane holding a resting GTC is *permanently* force-retire-only, on the ground that cancelling the order would be a trading decision the ceremony must not force. That ground does not survive §8's amendment of the same day. §8 accepted flatten-before-handover on the reasoning that every planned lane move — whole-machine migration, a host rebuild, retiring an untrusted lane, reshuffling accounts — lets the operator choose its own timing, so closing out first costs almost nothing. Cancelling a resting order before retiring a lane is the same act under the same reasoning and a strictly smaller one: a cancel realises neither a gain nor a loss. The two sections reached opposite conclusions about the same operator on the same day, and this is the one that stands.

So Decision 2's condition 3 reaches the resting GTC, and the reversal is stated plainly rather than implied: **on the normal retirement path the operator is now required to cancel a resting order, and a resting GTC no longer makes its lane permanently force-retire-only.** The gate's *strength* is unchanged and is not the thing being traded away — a resting GTC is still a working order, lane quiet is still not scoped around it, and the rejected alternative above (excusing it) is still rejected on its original grounds. What changes is which side of the gate the operator can stand on: before, no act of theirs could move them across it; now one can.

**`force-retire` is recast, not weakened.** It stops being the only retirement path for a served clerk and becomes the exit for a lane that **cannot answer** — crashed, host lost, unreachable, or holding an obligation its operator declines to discharge. For a lane that cannot answer, it is preceded by a step that sits outside every ceremony in this ADR: the operator cancels the orders and closes the positions **directly at the broker**, because a lane that cannot answer also cannot act on its own account. Its own preconditions are untouched — the two-legged deadline, the `outcome_unknown` settlement of each unsettled attempt, `lane_confirmation: absent`, the operator attribution — and it does not become a branch inside `retire`.

**Two cases the conditions see but the panel cannot discharge, and how they exit.** They are the same shape and take the same exit. `flatten_stop` reduces bot-attributed exposure and refuses manual-custody legs (`app/broker/alpaca/clerk/sqlite/safe_flatten_execution.py:104`), so a **position opened by hand** at the broker survives every action the panel offers; and `cancel_verified_working_orders` refuses anything but an owned ENTRY order (`app/broker/alpaca/clerk/sqlite/runtime.py`), so an **order placed by hand** survives it too — the more dangerous of the pair, because an order can still fill and re-open a position after a confirmation is taken. Conditions 3 and 4 read the whole account and therefore *see* both, which is the point of reading the provider's own lists rather than the lane's custody: the lane **refuses and names the outstanding item** instead of passing on a partial view that would have been silent about precisely what nothing in the lane can act on. The operator cancels or closes it at the broker and re-confirms. This is deliberately not a new ceremony — the lane cannot reduce or cancel what it holds no attributed custody for, and fabricating an unattributed reduction is the hazard §8's amendment already refused to build.

A stale heartbeat is never itself a gate — ADR 0062 Decision 4 forbids liveness from moving ownership, and no exception is carved. Staleness may corroborate an operator-initiated `force-retire`; it may not trigger one.

**Open gap, named rather than closed — and closed since, by #2111's implementation.** The forced-unknown correlation ids are recorded against a clerk that is then retired, and Decision 8 establishes that no successor can describe them, so they would have had no owner and no work queue. This ADR required `force-retire` to emit them to a durable record outside the retired clerk's row and deliberately did not specify its home. **It now has one:** `store.record_forced_correlations` writes them to an append-only registry table, in the retirement's own transaction, so a failure anywhere in the ceremony rolls the obligations back with it and no sidecar write can silently drop the queue. The gap is discharged; the paragraph is kept because the requirement it states is what the implementation must keep satisfying.

### 6. The `provisioned -> retired` bypass is closed against an observable

The trigger allows a direct `provisioned -> retired` edge for "a clerk that never served" (`schema.py:285-293`), but nothing defined or enforced "never served", and `retire_clerk` gates only on unreleased assignments while the CLI passes `--clerk-id` straight through (`scripts/manage_broker_fleet.py:767-770`). So `release-assignment` followed by `retire` skips the drain entirely — and `retire_clerk`'s own refusal text signposts that route.

"Never served" is made an enforced predicate, and it is genuinely observable because all three tables it reads are delete-proof at the schema: **no row in `account_assignment_history` for this clerk, no row in `clerk_session_history`, and no live row in `clerk_sessions`.** `retire_clerk` evaluates it in the transaction that performs the transition. A clerk that meets it retires directly. **A clerk that has ever served must pass through `draining`**, and `retire_clerk` refuses otherwise.

`retire_clerk`'s refusal text is re-authored to name the drain as the first step, not release. A ceremony nobody is obliged to run fails the same way a check that cannot fire does.

**`update_clerk_lifecycle` (`store.py:414-427`) has a second live caller**, and enforcing the predicate only in `retire_clerk` leaves it standing on a single-call-site convention while the schema trigger (`schema.py:285-293`) still permits `provisioned -> retired` unconditionally. The second caller is the provisioning-compensation path (`service.py:361-367`): when `write_volume_marker` fails after the registry row is committed, the half-born clerk is retired directly, with no predicate call. That specific write is legitimate today — a clerk whose marker write failed provably never served — but its legitimacy is an accident of who happens to call it, not a property the schema enforces. A future caller added to either path would silently inherit the bypass this section exists to close.

The repo's own pattern for exactly this shape is a trigger backstop behind a service pre-check — `schema.py:298-299` says so in as many words, for the volume-nesting fence: "the service's pre-check produces the typed refusal; this is the backstop a race cannot step over." That pattern is adopted here rather than left as a convention this ADR merely hopes every future caller honors: `trg_clerks_lifecycle_forward` (`schema.py:287-295`) gains a fourth `WHEN` arm that aborts a `provisioned -> retired` transition unless the clerk mirrors the enforced predicate exactly — no row in `account_assignment_history`, no row in `clerk_session_history`, and no row in `clerk_sessions` for `OLD.clerk_id` — **three `NOT EXISTS` clauses, mirroring the three-clause predicate above exactly.** The predicate itself was already three-clause; what is added here is that the trigger mirrors it rather than checking only the two append-only history tables, and the justification for why the third clause is load-bearing: `upsert_session` is `INSERT … ON CONFLICT(clerk_id) DO UPDATE` (`store.py:485-523`), so one row per clerk is installed and refreshed in place; `archive_session` (`store.py:468-483`) has exactly one caller, `register_agent_session` (`service.py:655-656`), guarded by `if current is not None`, so `clerk_session_history` is populated only when a *second* registration supersedes the first; and the live row cannot be removed — `trg_clerk_sessions_no_delete` (`schema.py:324-328`) aborts any delete with "a superseded session is archived, not deleted", and no `DELETE FROM` statement exists anywhere in `store.py` either. A clerk that registered exactly once therefore holds a live `clerk_sessions` row and zero history rows, and a trigger checking only the two history tables would abort nothing and let it through as never-served. `retire_clerk`'s check stays — it produces the typed, actionable refusal the trigger's `RAISE(ABORT, ...)` cannot — but the trigger is now the thing a race, or a future caller nobody thought to gate, cannot step over.

**In practice "never served" means "never booted", and that is the operational shape operators will meet.** Because the live `clerk_sessions` row is installed on first registration and never deleted, any lane whose agent has ever started holds one for life. The predicate is therefore not "has no obligations outstanding" but "has no registration in its history at all". Two consequences follow, and they pull in opposite directions:

- **A freshly provisioned lane that never started stays directly retirable.** It has no assignment, so `retire_clerk`'s existing held-assignment refusal (`service.py:452-461`) passes, and all three `NOT EXISTS` clauses hold. The direct `provisioned -> retired` edge still works for exactly the population it was written for; closing the bypass does not make a never-booted lane un-retirable.
- **A lane that started once and was never assigned now costs the full ceremony.** Drain, wait out the deadline, then `force-retire` — because lane quiet cannot be answered (#2154), a lane that booted once is a served clerk by this predicate even though it never held an account. This is accepted: the alternative is a predicate that reasons about what a booted lane *might* have done, which the coordinator cannot observe, and the ADR's standing rule is that an unobservable gate is worse than a slow one.

This backstop needs a read path the schema does not currently have: **`account_assignment_history`'s primary key is `(broker, canonical_external_account_id, assignment_generation, state)`** (`schema.py:406-417`), with no `clerk_id` column in any key or index, and its only reader, `list_assignment_history` (`store.py:740-750`), is account-scoped. Both the enforced predicate's read in `retire_clerk` and the new trigger's per-row lookup need a clerk-scoped read this table cannot serve today. A supporting index on `account_assignment_history(clerk_id)` is required alongside the partial index Decision 3 specifies for `routing_receipts`; `clerk_session_history` needs no equivalent addition, since `clerk_id` already leads its primary key (`schema.py:145-153`).

### 7. Failure modes

**7.1 Coordinator unreachable mid-drain.** Nothing is lost: no part of a drain is in memory, `draining_since_ms` is durable, the deadline is an absolute instant rather than a countdown, and every gate is recomputed per attempt.

**But ADR 0062 Decision 7's offline recovery path is a hole this ADR cannot close, and its blast radius is stated rather than hidden.** That path lets a verified original clerk recover its already-confirmed last-effective binding while the coordinator is unavailable. The first draft proposed that the path "read the durable lifecycle state from its confirmation evidence"; **it cannot.** `ConfirmationEvidence` (`confirmation.py:48-64`) carries eleven fields and no lifecycle state, is written at confirmation time — necessarily before any drain — and is never re-authored. A lane that confirmed while provisioned and later drained is byte-indistinguishable from a healthy one.

A partial mechanism *could* exist: since Decision 1 has the heartbeat return the lifecycle state, a lane that learns it is draining could re-author its evidence with a drain marker, and the offline path could then refuse. **It does not exist today.** It is not implemented, it is not among the prerequisite fixes this ADR lists in Consequences, and it has no owner. Describing the hole as though that mechanism were already narrowing it — present only for the case where a drain was issued against an already-unreachable lane — overstates what ships with this revision.

**Blast radius, stated plainly, in the present tense:** today, `fleet_boot.py:284-300` enters the offline path on *any* `FleetPresenceError` from `presence.register`, then boots the last-effective binding from the evidence file alone via `offline_boot_matches` (`fleet_boot.py:385-404`); and `register_agent_session` (`service.py:571-572`) refuses only `RETIRED`, never `DRAINING`. Nothing here distinguishes a lane drained *before* an outage from one drained *during* one — because the re-authoring mechanism that would draw that distinction does not exist, every drained lane that restarts while the coordinator is unreachable takes the offline path indistinguishably from a healthy one, reopens its binding via FR-066, and may execute against an account the operator had closed its door on. The window is bounded by coordinator unavailability, but the population it applies to is **any drained lane**, not only one drained while the coordinator happened to already be unreachable. It is not closed by this ADR (tracked as #2155). Closing it requires either a lifecycle field in the confirmation evidence written at drain time by a path that does not depend on the lane being reachable, or the offline recovery path consulting something other than the evidence file. **Reassignment must not be performed against any drained lane until this is closed**, because restart-during-outage is not a distinguishable subset today — it is the general case. Read against §4.1, which requires reassignment's predecessor to *be* draining, this is not a caution about a subset of lanes but a total block: the two constraints leave reassignment no legal predecessor state at all. §4.1 draws that conclusion out and records why it is accepted.

**Amendment (2026-09-21, closing #2155): the mechanism this section said did not exist now ships, and this section's general-case blast radius narrows to a residual window that is stated rather than hidden.** The heartbeat's answer now carries the clerk's lifecycle (`observe_session` returns it; the internal surface's `sessions/observe` body names it), and `register_agent_session` and `confirm_assignment` refuse a `draining` clerk with the typed `clerk_lane_draining` — a refusal deliberately distinguishable from unreachability, which both presence transports translate to one lane-side type (`fleet_lane_draining`) that FR-066's offline fallback does not catch. A lane learns its drain through either channel and re-authors its confirmation evidence the same moment: schema v2 adds `lifecycle_state` (v1 files read back as `provisioned` and keep their FR-066 story), a learned drain flips the file to its drained tombstone under the writer's own identity and durability rules, and both `offline_boot_matches` and the offline boot path itself refuse marked evidence — the resurrection path this section described is closed for every lane that learns its drain. A draining lane also starts no new bots once it learns. **The residual window:** a lane unreachable for the *entire* drain never receives either channel — its evidence stays unmarked (a v1 file, which carries no lifecycle field, and a v2 file whose `lifecycle_state` was written `provisioned` at confirmation time are alike unmarked), and if it then restarts during a coordinator outage with no reachable-coordinator contact in between, the offline path still boots its last-effective binding. That population is not empty and not closed here; it is bounded by the operator's own drain procedure (the runbook's step: after `drain`, watch for the lane's next heartbeat — a live lane marks within one interval of the drain, and a lane that fails to return it, or was already down at drain time, is being decommissioned anyway, so its volume is treated as part of that retirement, not restarted) and shrinks to the empty set as a lane only when #2154's confirmation push lets the coordinator *know* the drain reached the lane. **The reassignment block therefore stands, on moved ground:** not because resurrection is the general case (it no longer is), but because a coordinator cannot yet distinguish a drained-and-drained-quiet lane from a residual-window lane, and until #2154's lane-quiet confirmation exists it must not try. §4.1's conclusion is unchanged in force and updated in ground by its own amendment below.

**7.2 The draining lane crashes mid-drain.** Its session goes stale; per ADR 0062 Decision 4 that transfers and releases nothing, unchanged. Exposure does not widen — a draining lane is unroutable regardless of liveness — but its testimony is lost, so Decision 2's gate cannot be satisfied and Decision 5's `force-retire` is the only exit. The registry never writes a confirmation the lane did not give, and never reads silence as assent.

**7.3 A drain against an already-draining lane.** Idempotent: the existing record returns with `draining_since_ms` untouched, mirroring `open_routing_attempt`'s same-key resume (`service.py:1391-1400`) and `reserve_assignment`'s same-owner resume. Re-draining must not extend the deadline, or a retry loop makes the bound decorative.

Drain is irreversible; the trigger already refuses `draining -> provisioned` (`schema.py:287-293`). An operator who drains the wrong lane provisions a new one. This matches retirement's terminality and ADR 0062 Decision 3's non-recycled identities, and is accepted rather than worked around.

### 8. Scope boundary: the fleet layer hands over the account, not the account's work

No gate in this ADR reads a position, and none may be added. (Narrowed 2026-09-19 by Decision 2's amendment: the *fleet layer* still reads no position and stores none, and condition 4 gates retirement on a flat account the **provider** computed against its own broker connection and reported as one bounded fact — which is the same provider-owned nothing-open evidence this section's own amendment below requires for handover. What may not be added is a position read *by a gate in the fleet layer*.)

A successor receives the reserved right to write to the account — not the predecessor's custody, ledgers, receipts or runner state, for the reasons in Context. Reconstructing the account's live positions into the successor's custody is provider-owned under ADR 0035/0047, and **no such adoption ceremony exists.** Until it does, a reassignment leaves open positions at the broker with a successor whose custody does not describe them: safe to pause in (the successor is reserved, not confirmed, so execution routing stays closed per `service.py:1300-1315`) and unsafe to resume from. **Reassignment must not be exercised against an account with open positions until that ceremony ships** (#2150). This is an *independent* prohibition, narrower than §4.1's: §4.1 and §7.1 jointly block reassignment against every drained lane whether or not it holds positions, and this one would still stand for an unpositioned account if #2155 closed tomorrow. Drain, release and retire are useful without either.

**Amendment (owner decision, 2026-09-19, resolving #2150): the adoption ceremony is rejected, and the prohibition above stops being interim.** #2150 posed the choice — build adoption, or make flatten-before-handover the enforced rule — and what decided it is when lane switches actually happen. Every planned move — whole-machine migration (#2151, the preferred route), a host rebuild, retiring an untrusted lane, reshuffling accounts — lets the operator choose its timing, so closing positions first costs almost nothing, and the priced recovery-flatten machinery that shipped with #2229 (after-hours re-drives, releasable folds) makes even a stressed flatten reliable. The one scenario that argued for adoption — unplanned host death with open positions — destroys the predecessor's records with the host, so inheriting them cannot serve the only case that needs it: the successor could not even flatten what it inherited, because a reduction's quantity is derived from the reducing lane's own durable attributed custody (`app/broker/alpaca/clerk/sqlite/safe_flatten_execution.py`), and the volume holding that attribution is the thing that died. What could serve that case is reconstructing custody from the provider's own position list — a provider-owned rebuild that doubles as the lost-records recovery path. That, not predecessor-record inheritance, is the only future capability this decision contemplates, and it is unscheduled.

**An account holding open positions or working orders is not handed to a successor — not by reassignment, and not by release followed by reserve (#2157's two-step reach of the same handover, `service.py:824-838`, closed to the ceremony's gate by §4.1's 2026-09-22 amendment); the operator flattens first.** Enforcement is deliberately not a standalone refusal on `reassign_assignment`: alone it is walkable via the two-step path, and this section's first sentence still forbids the fleet layer reading a position. It arrives as provider-owned nothing-open evidence — Decision 2's lane-quiet shape, counting positions *and* working orders, a resting GTC included per Decision 5 — required on both handover paths, and it is a requirement on these ceremonies' implementation (#2111), recorded there. Until it ships, the prohibition stands exactly as this section states it; reassignment is unreachable regardless (§4.1, §7.1).

The 2026-09-15 rejection of a flat requirement is not reopened. Drain and release stay flat-free — a lane may stop serving and be released while positioned, and the account sits unassigned with its positions at the broker for as long as the operator chooses. What 2026-09-19 narrows is successor acquisition and, by Decision 2's amendment, retirement on the normal path; drain entry and release are untouched and stay flat-free. The residual cost is stated rather than hidden: unplanned host death with open positions forces manual reconciliation at the broker, outside every ceremony. It is accepted for two reasons — overnight exposure is sized so a manual cleanup is an annoyance rather than an emergency, and the provider-side rebuild above is the honest relief valve if that ever stops being true.

## Considered and rejected

**Gate the drain on routing receipts as an order ledger.** This was the first draft's central decision and it is withdrawn. Receipts settle on the HTTP response (`routing.py:485-489`), most orders never enter them, streams never enter them, and the table leaks (`routing.py:444`). It would have been a gate that always passes.

**Gate on `_inflight == 0`.** Rejected on the four counts in Context.

**Keep an unconditioned degraded path so retirement always has an exit.** Rejected: an always-available degraded path makes the gate above it optional structurally, not merely until an adapter ships. Decision 5's `force-retire` is deadline-conditioned, separately named and attributed.

**Let a stale heartbeat complete the drain.** Rejected on ADR 0062 Decision 4's grounds; a partition must never manufacture a second writer.

**A background reaper.** Rejected on ADR 0047's grounds: it makes the riskiest step the one nobody watched, for the sake of saving one command.

**Require the account flat.** Rejected by owner decision, and correctly — it would make every infrastructure move a trading decision. (Narrowed 2026-09-19 by Decision 2's amendment, which gates *retirement on the normal path* on a provider-computed flat. The rejection survives where it bites: drain entry and release stay flat-free, and `force-retire` keeps a positioned lane's exit open on its own deadline, so no infrastructure move is forced through a trading decision.)

**Scope lane quiet to exclude a resting GTC order.** Rejected, and Decision 5 states the cost of rejecting it. It would have made lane quiet satisfiable for every lane once a provider ships it, at the price of a gate that passes while a real, named obligation is still working at the broker — the same failure as `RELEASE_PROOF_TOKEN`, relocated into a definition instead of a table. It would also contradict `CONTEXT.md`'s own order-quiet entry, which this ADR authored. The accepted cost *was* that a lane holding a resting GTC is `force-retire`-only. **Decision 5's 2026-09-19 amendment reverses that cost, not this rejection:** the operator cancels the resting order on the normal path, on the same reasoning §8 used to accept flatten-before-handover. Excusing a resting GTC from the definition stays rejected on the grounds above — what changed is that an operator now has an act that carries them across the gate, where before none existed.

**Keep the token alongside the new gates.** Rejected: a gate that adds nothing but is present teaches operators that gates are formalities.

**Ship the ceremony with order-quiet unstated, gated on what is observable today.** Rejected as the worst option available. It would produce a ceremony that looks complete, passes on every healthy lane, and silently fails the one constraint the owner made binding.

## Consequences

- **The ceremony is honest about ordering, and incomplete on purpose — and it does not ship "blocked."** Drain entry, the bypass closure and its trigger backstop, command quiet, the release precondition (including the deadline wait, §4.1) and `force-retire` are implementable now. Two paths are not, for two different reasons with two different end dates: `draining -> retired` on the normal, unforced path is blocked until a provider can answer lane quiet (#2154); and **`reassign_assignment` is unreachable outright** — §4.1 requires a draining predecessor, §7.1 forbids one, and the block lifts only when #2154 closes: #2155's resurrection hole is closed by §7.1's amendment, and the block now stands on that amendment's residual window plus the still-missing lane-quiet confirmation (§4.1's amendment states why that is accepted, and #2151/#2150 why it costs little). Its precondition is still specified, because it is what the implementation must build once #2154 closes, not because the ceremony runs. **Retirement's normal path is not the one that ships for any served clerk either.** Since no provider can answer lane quiet today, `force-retire` is not an exception — it is the only path to retirement for a served clerk, 100% of the time, and the auditable count of forced retirements starts at 100% and stays there until #2154 closes. An operator retiring a served clerk today runs an attested, deadline-delayed, audited `force-retire`, not the unforced path; describing the ceremony as shipping "blocked" without saying that is the document failing its own standard.
- **Amendment (owner decision 2026-09-19, details confirmed 2026-09-21, closing #2154): the 100%-forced figure gets an end date, and the population that stays forced is named.** Once the lane-quiet confirmation ships, a served clerk whose operator stops its bots, cancels its working orders (a resting GTC included, per Decision 5's amendment) and flattens its account retires on the **normal** path, and the auditable count of forced retirements falls below 100% for the first time. It does not fall to zero, and the residue is not an accident: a lane that cannot answer — crashed, host lost, unreachable — still exits through `force-retire`, and so does one whose operator declines to discharge an outstanding obligation. The count stays worth reading for exactly that reason. **Reassignment's block lifts with the same change but not by the same breadth**: §4.1's amendment blocks it until #2154 closes, and §7.1's residual window shrinks "to the empty set as a lane only when #2154's confirmation push lets the coordinator *know* the drain reached the lane" — a lane-quiet confirmation is that knowledge, so reassignment becomes reachable against a predecessor **that confirmed**, and stays blocked against one that never did. The RELEASED-reservation consequence §4.1's 2026-09-22 amendment accepted lifts on the same terms: an account released from a lane that confirmed lane quiet can be reserved again.
- **What closing #2154 costs, sized honestly — and the bullet above is part of the bill.** The lane-side enforcement is already in place: #2155 shipped the drain-learning latch (`fleet_boot._learn_drain`) and the new-run refusal (`app/services/bot_runner.py::drained_lane_start_gate`), which is condition 1. **What does not exist**, in the order a build would take it: (1) a provider fact computing conditions 2–5 against the Alpaca clerk's own custody database and broker connection and returning one bounded answer with its observation instant — `reconcile._read_account_snapshot` already performs the account-scoped order-and-position read conditions 3 and 4 need, *including* refusing at the 500-row boundary because completeness cannot be proven, so this composes that helper rather than duplicating it; (2) a durable home for the confirmation, which `clerks.lane_confirmation` is **not** — that column records the retirement's *outcome* (`present`/`absent`), not the evidence, its instant, or the session that asserted it — so schema v6 adds an append-only `clerk_lane_confirmations` table under the registry's existing immutability and no-delete triggers, keyed on its own append sequence — **not** on `observed_at_ms`, which an earlier revision of this bullet specified and which building it proved unsafe: the lane supplies that instant, so keying or ordering on it lets a host whose clock stepped back pick which of its own answers the gate reads — and the gate reads the newest row **for the current session**, which is what makes "does not survive the session that made it" a query rather than a cleanup; (3) a confirmation route beside `/internal/fleet/assignments/confirm` and its `FleetPresence` method on both `LocalPresence` and `RemotePresence` (internal agent↔coordinator only — these routes are absent from `contracts/openapi/python-data-service.openapi.json`, so the "no OpenAPI or frontend regeneration" claim above holds for this change too); (4) `_require_lane_quiet` reading it instead of raising unconditionally. **No new refusal-vocabulary entry is needed** — an earlier revision of this bullet claimed one per outstanding condition, and building it showed otherwise: `clerk_lane_quiet_unproven` already names the fact the gate is refusing on, and which condition is outstanding belongs in the message, exactly as every other multi-cause refusal in this service carries its specifics. A reason code per condition would have made the vocabulary a duplicate of the condition list. **And the four items the bullet above promises that an inventory stopping there would under-count:** (5) `release_assignment` records `lane_confirmation: absent` unconditionally today (`service.py:1549`), so no released row can ever read *confirmed* until it consumes one; (6) `reserve_assignment`'s released branch refuses unconditionally and must learn to consume it; (7) the transactional transfer behind `reassign_assignment`'s refusal — the code comment there states outright that `store.reassign_assignment` "arrives with #2154's unblocking change", so the whole transfer path is in this bill; and (8) a **third** runbook beyond the two this ADR's inventory already names — `docs/runbooks/add-an-alpaca-account.md` prints the force-retire-only retirement sequence verbatim. **Before building the predicate, read the two shapes that already approximate it** so this does not become a third near-duplicate (guiding philosophy #5): archive's eligibility proof — "the registration is stopped, flat, and has no working orders" (`app/broker/v2panel/action_policy.py`, ADR 0052) — and `InstanceCustodyProof`'s `working_order_refs`/`unresolved_intent_refs` pair. Neither is account-scoped, which is the gap; both are the right starting point.

  **Amendment (2026-09-22, review of the coordinator slice): two of the three starting points named above do not compute what this decision requires, and the provider slice must not compose them as-is.**
  - **Condition 5 needs the account-wide nonterminal effect read, not `InstanceCustodyProof`.** `unresolved_intent_refs` is built from `_unresolved_order_refs` (`sqlite/runtime.py:1487`), which draws on `repo.uncertain_orders()` — documented as "every order whose effect operation is still `unknown`" (`sqlite/reads.py:728`). A newly durable ENTER or EXIT is first stored `accepted` with a NULL `broker_state`, *before* the broker call, so during that window `working_order_refs` and `unresolved_intent_refs` are **both** empty while the intent can still create custody. The file already concedes the helper's blind spot in its own docstring at `:1477`. `reconcilable_effect_operations(subject_id=None)` (`sqlite/reads.py:554`) is the read that fits: account-wide, and `state NOT IN ('succeeded','failed','rejected')` so it counts `accepted` too. Condition 5 reads that, and `InstanceCustodyProof` is cited above only as prior art for keeping the two sets apart.
  - **`_read_account_snapshot` cannot establish conditions 3 and 4 "at one observed instant".** It issues `list_orders()` and `list_positions()` through `asyncio.gather` with no common snapshot or consistency fence (`sqlite/reconcile.py:509-512`). If positions reads flat and an open order fills before orders reads, both come back empty while the account is positioned — a false quiet answer, and the gate cannot tell. Composing it unchanged, as this bullet's item (1) instructed, is therefore not sufficient. The provider slice owes a conservative stabilization rule instead: re-read after the pair and refuse unless nothing changed across the re-read, so a fill landing mid-snapshot is *seen* rather than averaged away. Its 500-row refusal remains the right precedent — completeness that cannot be proven refuses.
  - **A confirmation is not bound to the account it was computed for.** The row carries clerk, session, epoch and instant, and nothing else; but conditions 3 and 4 are facts about *an account*. `ix_account_assignments_owner` is a plain non-unique index (`schema.py:262`), so one clerk may hold several live assignments. This is harmless for retirement, which requires every assignment released before the gate runs — but items (5)–(7) consume the same confirmation to authorize release, reservation and transfer *of one named account*, and there a confirmation computed for account A would authorize moving account B without ever having looked at it. Before those items ship, either the confirmation carries the broker-qualified account identity and pinned assignment generation and the consumer checks them, or one live assignment per clerk becomes a structural constraint. Deferring this to the implementation is what this inventory exists to prevent.

- **Delivered so far (#2154, coordinator side).** Items 2 and 4 above ship together: schema v6's append-only `clerk_lane_confirmations`, the fenced `confirm_lane_quiet` entry point, and `_require_lane_quiet` reading the newest answer for the clerk's current session instead of raising unconditionally. **The table is keyed and ordered on the registry's own append sequence, never on the lane-supplied `observed_at_ms`** — a lane host whose clock steps back would otherwise choose which of its own answers the gate reads, and could retire itself on a quiet claim it had already withdrawn; the instant is kept because freshness is measured against it, never to order or identify a row — so `draining -> retired` completes on a confirmed lane for the first time since this ADR was accepted. Items 1 and 3 (the Alpaca provider fact and its transport) are what make a real lane able to answer; until they ship, the gate is reachable only through the service API, and no production lane confirms. Items 5-7 — release, reserve and the transfer — remain outstanding, and §4.1's amendment states why they are not optional: wiring the confirmation into retirement alone closes this ADR's gate and leaves the two-writer hole it named open.
- **Delivered (#2154, provider side, 2026-09-22).** Items 1 and 3 ship: the Alpaca lane answers. `app/broker/alpaca/clerk/sqlite/lane_quiet.py` computes conditions 3-5 from the account's own open-order and position lists (`reconcile.read_account_open_work`, the one account read reconciliation also uses) and from `reconcilable_effect_operations` account-wide, and `fleet_boot.lane_quiet_probe` adds condition 2 from the bot runner's own tasks, read before and after the account so a bot still winding down cannot slip between. **The re-read rule** the Codex correction owed: the order and position reads carry no consistency fence, so the lane answers quiet only when two complete reads, the second issued after the first returned, both found the account empty with the intent read between them empty too; what can escape is work that opened *and* ended between two reads and left the account empty, which leaves nothing to hand over. An unreadable broker is no answer, never a "not quiet" one. The draining lane pushes a fresh answer on every heartbeat through `FleetPresence.confirm_lane_quiet` (both presences) and `/internal/fleet/lanes/confirm-quiet`, whose body is strict — a missing condition is malformed, never defaulted — and a failed observation is logged and retried rather than ending the beat. A lane that learns its drain with no clerk to answer from says so once in its log. The auditable forced count therefore falls below 100% for the first time; it does not reach zero, because a lane that restarted mid-drain, lost its host or has no clerk still cannot answer. Items 5-7 are unchanged and still outstanding.
- **Delivered (#2154, handover side, 2026-09-22) — #2154 closes.** Items 5-7 ship, through the one shared gate (`_require_lane_quiet`, now returning the confirmation it accepted). **The account-identity precondition is met structurally, not by a column:** schema v7 makes `ix_account_assignments_owner` a UNIQUE partial index, so a clerk holds at most one live assignment, and a draining clerk reserves nothing — its confirmation can therefore be about only the one account it held when the drain began, and the row stays identity-free as §8 prefers. The v7 upgrade refuses, and rolls back, on a registry already holding two live assignments for one clerk, because which is real is not the schema's to decide. `release_assignment` stays available — it is the fleet's only exit — but records `present` only when a fresh, quiet confirmation from the owner's current session covers it, and `absent` otherwise. `reserve_assignment`'s released branch reads that recorded fact: it transfers the account to the reserving lane at the next generation only when the release recorded `present` **and the old lane has since been retired**, still requires the successor's volume proof, and refuses a successor that already holds a live assignment; an `absent` release keeps #2157's typed `ClerkReassignmentBlocked`. `reassign_assignment` runs every §4.1 precondition, then requires the predecessor's fresh, quiet confirmation, then releases, **retires the old lane with `lane_confirmation: present`**, and reserves for the successor in one transaction. `reassign_assignment` also moves an account that is already released, through the same released-branch gate, because a lane booting over `RemotePresence` carries no volume proof and so cannot take a released account itself — the host ceremony, which carries the successor's volume root, is that path's reachable route, and it records the operator's attribution on the successor's reservation. **Every handover ends with the old lane retired**, for two reasons found in review: a retired lane can never re-register or be routed to, so the release's durable `present` is not left standing beside a lane that could still be reached; and the old lane's clerk keeps reading the account it was composed against, so once a successor trades that account the old lane could never read quiet again and would be pushed into `force-retire` — retiring it first, on the answer the handover already accepted, is what keeps both lanes on the unforced path. The confirmation also answers §7.1's residual window: a lane confirms only after it has learned its drain, and learning it tombstones the volume evidence an offline boot would resurrect, so a confirming lane is exactly one the drain reached. **What stays open, stated rather than discovered:** an account released `absent` — its lane could not answer — cannot be re-reserved by any lane and has no recovery ceremony; re-onboarding it would need a separately attested proof that the old lane's volume and credentials are gone. The named residual in Decision 2 (an operator acting between confirmation and handover) is unchanged, and narrower here, because a drained lane accepts no routed work.

Change 4 is not: a trigger arm that aborts `provisioned -> retired` alters the behaviour of rows that already exist, so a registry upgraded to v5 refuses a transition it would have accepted at v4. ## Anti-patterns rejected

- A fixed proof string, or any attestation whose expected value is published in the artifact that checks it.
- Presenting a gate as measuring orders when it measures HTTP round trips, outcome bookkeeping, or process-local capacity.
- An unconditioned degraded path beneath a gate, which makes the gate optional.
- Gating a lifecycle transition on a per-process in-memory counter a restart resets.
- Treating a count as evidence where a set is needed.
- Letting heartbeat silence release, transfer or retire anything.
- A background process that settles command outcomes or retires lanes unattended.
- Recording a lane confirmation the lane did not give, or reading its absence as assent.
- Leaving a ceremony optional by preserving an unenforced direct path around it.
- Extending a drain's deadline on a repeated drain request; making a drain reversible.
- Requiring the account flat, or reading a position, in any *drain-entry* or *release* gate; and the fleet layer reading a position anywhere. (Narrowed 2026-09-19 by Decision 2's amendment, which gates *retirement on the normal path* on a flat account computed by the provider and reported as one bounded fact. `force-retire` keeps a positioned lane's exit open, so no ceremony forces a trading decision.)
- Claiming a successor inherits custody, ledgers, receipts or runner state from a volume it never mounted.
- Any timestamp here that is not `int64 ms UTC`.
