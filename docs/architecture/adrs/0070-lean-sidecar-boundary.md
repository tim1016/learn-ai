# ADR 0070 — The LEAN sidecar is a pinned reference engine, launched by a separate process inside a hardened container

**Status:** Accepted 2026-09-30
**Provenance:** Entry 4 of [#2745](https://github.com/tim1016/learn-ai/issues/2745), merged from #2742 C, #2743 C and #2741 kept why 4. The boundary, the runner pin and the execution policies were designed in the LEAN Sidecar Lab architecture doc during Phases 1–5 (2026-05). Owner decisions D2 (2026-08-12), D3, D5 and D10 (2026-05-18) come from the sidecar's mission-critical decision list, which a later clean-up slice deletes once this ADR holds them. Written by [#2749](https://github.com/tim1016/learn-ai/issues/2749).
**Vocabulary:** none owed — the sidecar is a research and validation tool, outside the live trading and operator domain that `CONTEXT.md` covers.
**Related:** ADR 0069 (reconciliation taxonomy and tolerances), ADR 0049 (the data lake is the market-data authority; §1a scopes the LEAN on-disk format), ADR 0058 (backtest runs owned by Python), ADR 0061 (golden validation over paired Python and LEAN run evidence), ADR 0022 (`int64 ms UTC` at the parse boundary).

## Context

QuantConnect's LEAN is the reference for most of the trading math ported here. Running real LEAN beside the Python engine gives three things a vendored source extract cannot: compatibility with QuantConnect-style `QCAlgorithm` code, reference traces to reconcile the Python engine against, and audit evidence of what LEAN actually does on a given input. LEAN is a .NET runtime that executes algorithm source. Starting it from inside the data plane would hand that source the data plane's network, secrets and host. And a LEAN run that silently drifts (a floating image tag, adjusted prices fed to raw-mode semantics, a forward-filled bar, a window that consumes no data) produces evidence that looks clean but is wrong.

## Decision

1. **LEAN is a reference engine, never the canonical one.** The Python engine (`PythonDataService/app/engine/`) stays canonical (ADR 0068). The sidecar exists for compatibility runs, reconciliation traces and audit evidence. Its per-run outputs are evidence, not registered math. Making LEAN canonical for anything takes a new decision.
2. **A separate launcher process alone owns Podman.** `app/lean_sidecar/launcher/` runs beside the data plane. It has three routes. `POST /launch` and `POST /extract-metadata` both require a shared-secret `X-Launcher-Token` (`launcher_auth.py`); `/extract-metadata` copies the pinned image's metadata databases, so the data plane never needs Podman. `GET /healthz` is unauthenticated: it reports only reachability and whether the pinned image is available. The data plane reaches the launcher only through `launcher_client.py` and never receives the Podman socket. A launch request carries the run id, the image digest, the limits and a few flags, but never a host path. The launcher resolves `run_id` to a workspace under its own configured artifacts root and refuses any path that resolves outside it. It resolves the lake root from its own configuration too. Why: mounting the socket into `polygon-data-service` would turn any exploited FastAPI handler into full host control.
3. **The image is pinned by digest.** `app/lean_sidecar/config.py` holds the digests: the arm64 derivative with the .NET 10.0.9 runtime as the default, amd64 as opt-in, and one historical digest kept only to regenerate committed reconciliation fixtures. HTTP launches never use the historical digest. `:latest` is never resolved. `LeanRuntimeProvenance` records the LEAN version, the source commit and the binary hashes. The image is run directly, not through `lean-cli`, because the CLI adds account and login state and the dependency should be only Podman plus a digest. An upgrade is deliberate: bump the upstream digest, rebuild, capture the new digest, update `config.py` in one PR, and re-validate the fixtures.
4. **Every run gets the same hardened container, and every flag maps to a boundary.** `app/lean_sidecar/runner.py` is the only code that starts a container that runs algorithm source. Every run uses `--rm --network=none --security-opt=no-new-privileges --cap-drop=ALL --read-only`, and the launcher's own UID and GID as the container user (`runner.py::_container_user_spec`), with `--userns=keep-id` when Podman is rootless. A run is non-root only when the launcher is non-root. **Owed (#2769):** refusing a root launcher. Under one, today's container user is `0:0`. It gets at most three mounts:
   - the run's workspace, read-write;
   - a read-only overlay of the workspace's `data/` subtree, when requested, so user code has no writable alias for replacing an input between receipt checks;
   - in lake mode, the data lake mounted read-only, at a host path the launcher resolves from its own configuration.

   The repo root, `.env`, the host home and the Podman socket are never mounted, and the environment comes from a fixed allow-list. The security-flag viability matrix (`tests/lean_sidecar/test_security_flags.py`) is the evidence that the pinned image tolerates each mandatory flag. Optional flags come only from `ALLOWED_HARDENING_TOKENS`, which lists literal tokens, never patterns. Adding a flag, or a new value for one, is an edit to that set and to this ADR.
5. **Every run has mandatory limits.** `RunLimits` (cpus, memory, pids, wall-clock timeout, workspace size, log tail) are all required. The launcher refuses a missing or non-positive value. The defaults are `DEFAULT_RUN_LIMITS`: 2 CPUs, 3 GiB, 512 pids, 7,200 s, a 512 MB workspace and an 8 MiB log tail. The launcher's outer wall-clock kill applies in addition to anything inside LEAN. `--storage-opt` cannot cap a bind mount, so the workspace cap is enforced by polling the mounted workspace at a fixed interval that no caller can widen. Each request has input ceilings: algorithm source up to `MAX_ALGORITHM_SOURCE_BYTES` (256 KiB), and window caps in the router.
6. **Caller-supplied source runs only inside that container.** Strategy Lab's LEAN mode may submit `QCAlgorithm` Python source (`algorithm_source`; the entry class is `MyAlgorithm`). It never executes in `polygon-data-service`, the Backend or the Frontend. Such a run is a **compatibility run**. It executes the algorithm as written, and its manifest records whatever brokerage policy the algorithm chose.
7. **The LEAN data folder is a numerical contract.** Minute data follows LEAN's zip layout. Times are milliseconds since midnight ET. Prices are integer deci-cents, written through the lake's canonical encoder (ADR 0069 §8; ADR 0049 §1a). Raw dollars are forbidden: LEAN would divide them by 10,000 and still finish with garbage. A resolution, security type or session the sidecar has no proven layout for fails fast. It is never staged best-effort.
8. **Reconciliation-grade evidence is defined narrowly, and only part of the definition is enforced today.** A run counts as reconciliation-grade, meaning it may be compared against the Python engine, only when all of these hold:
   - its bars are raw and its corporate actions come from LEAN factor and map files, never from pre-adjusted bars. Adjusted bars plus factor files double-adjust, and adjusted bars without them get raw-mode semantics over adjusted input;
   - its algorithm is a bundled template that pins brokerage and fees. `trusted_templates.py` binds each template's source to its brokerage policy (`interactive_brokers` for the reconciliation templates), and those sources set starting cash, `fillForward=False` and raw normalization. Otherwise `SetHoldings` sizing and the bar stream diverge even when signals agree. Caller source is never inspected for these settings, so it is never reconciliation-grade;
   - its prices and fills are compared no tighter than LEAN's quantization floor, `atol=0.0001, rtol=0`;
   - the comparison covers orders, fills, positions, trade P&L and the equity curve. LEAN's aggregate statistics are version- and definition-sensitive, so they stay LEAN-native diagnostics until a statistic-level fixture pins each formula.

   The manifest records `data_adjustment_policy`, `data_normalization_mode`, `fill_forward`, the brokerage policy and the market-hours and symbol-properties databases. For caller source these fields are labels; the code does not introspect them.

   **Enforced today:**
   - In lake mode, a symbol with no factor file is refused at mount (`lake_mount.py`, `lake_factor_file_missing`).
   - A map file is optional. A mounted one must parse and cover the whole run window (`lake_map_file_unreadable`, `lake_map_file_window_mismatch`), because LEAN reads the symbol as delisted after the map's last row.
   - Fixture and non-lake runs stage empty `factor_files/` and `map_files/` directories (see D5 below).
   - A staging fetch that gets zero bars from Polygon is refused (`polygon_returned_zero_bars`, `app/services/lean_sidecar_service.py`).

   **Owed, not enforced:**
   - Alignment of the requested, staged and effective windows. The manifest records all three, but nothing refuses a mismatch, and LEAN can finish "green" over a window it never saw.
   - Failing a run that consumed zero bars. `_count_bars_consumed` records `{}` when the algorithm wrote no observations, and the run still succeeds.

   LEAN's result timestamps (unix seconds, often floats) become `int64 ms UTC` at one parse boundary (`normalized_parser.py::_unix_seconds_to_ms_utc`).
9. **Owner decisions carried from the mission-critical list.**
   - **D2, determinism gate (2026-08-12).** A determinism check reruns the trusted sample twice with the same image, data and config. The normalized LEAN execution-state envelope may differ only in `state.StartTime`, `state.EndTime` and `state.Hostname`, because they record the wall-clock invocation and the ephemeral container, not backtest semantics. LEAN's timestamped packaging files (`full_result`, `summary_result`, the launcher log, the request audit files) need not be byte-identical. The parsed normalized result with those three fields removed must be equal, and so must the byte-stable evidence (`data_monitor`, `observations`, `order_events`). No other exception is implied. Any other difference is a determinism bug. No golden fixture or reconciliation claim is accepted from a runner that has not passed this check.
   - **D3, reconciler scope (2026-05-18).** Self-reconciliation compares LEAN's recorded fees with the canonical `IbkrEquityCommissionModel`. Cross-engine reconciliation compares LEAN's trades with the Python engine's on the same algorithm and inputs. Pairing is **caller-supplied**: the request names the Python strategy, and no naming convention pairs runs automatically, because explicit is safer. Gating is **strict**: every `DivergenceCategory` gates except `COMMISSION_DRIFT`, which is diagnostic by default, because fee-model precision is a tunable comparison, not a strategy-logic claim. `COMMISSION_DRIFT` also gates when the caller sends `assert_fees=true` on a reconciliation-grade template with IBKR pinned on both sides (Branch A, as in `qc_reconciler.py`). Data is **shared**: the Python side runs on the same workspace zips LEAN saw.
   - **D5, data sources (2026-05-18).** Quotes stay synthetic: bid = ask = trade close, size 0 (`staging.py::stage_quote_bars`). Real NBBO waits until an algorithm that consumes quotes lands. Massive.com is the recorded candidate vendor, since the Polygon Starter plan gives no real NBBO, but adding any real-data vendor needs the owner's explicit go-ahead. Where no lake-built factor and map files are staged, the directories are empty, and a reconciliation-grade claim is bounded to windows with no corporate actions on the staged symbol.
   - **D10, reconciler output schema (2026-05-18).** The reconciler's response shape may change only with an explicit integer `schema_version` on the response. A consumer reads it and fails fast, with a visible error, on a version it does not recognize. A semantic change (same field name, new meaning) always needs the owner's decision, whatever the version says.

## Consequences

- Operator procedure (building the image, pinning a digest, Windows/Podman placement) belongs in a runbook. The decisions stay here.
- Each of these is a change to this ADR, not a code tweak: widening `ALLOWED_HARDENING_TOKENS`, dropping a mandatory flag or limit, or resolving an image by tag instead of by digest.
- A reconciliation that fails D2's check, or that lacks one of decision 8's pins, is not reconciliation-grade evidence, however clean its numbers look.

## Considered and rejected

- **The Podman socket mounted into the data plane.** Rejected. Any handler exploit would mean full host control.
- **`lean-cli` instead of the image.** Rejected. It brings login and account state into a server flow and adds a dependency surface.
- **Auto-pairing runs by name, or treating `COMMISSION_DRIFT` as gating by default.** Rejected in D3.
