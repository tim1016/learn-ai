# ADR 0065 — A worker's lease is a research job's liveness, and an interrupted Recency launch resumes like a Grid Search

**Status:** Accepted 2026-09-20
**Provenance:** Issue #1938, filed from the #1937 review: redelivered research job ids were made safe by refusing them (409) once closed, which left a crashed run unresumable — and the "is it running?" answer those refusals and presentations depend on was a Redis status field that keeps saying `running` after the worker is gone. The four hazards of replaying a closed job were enumerated in the #1938 scope note.
**Related:** ADR 0055 §4 (the attempt fence this extends to Recency), ADR 0057 (the Recency tables; its cutover note "relaunch under a new launch id" is superseded for interrupted launches by this Finish-style resume), ADR 0056 (the Finish shape Recency now copies), #1937 (the 409 redelivery guard this relaxes for `resume_launch_id`).

## Decision

1. **Liveness is the lease, not the status.** A dispatched worker acquires `job:{id}:lease` (TTL 300 s, `JOB_LEASE_TTL_SECONDS`); the worker renews it with every event emit and every gated cancellation check — the calls it already makes when it makes progress. There is no heartbeat thread: a heartbeat would keep proving liveness for a worker that has hung, which is exactly the case the status fields already got wrong. `job_is_live` (the single liveness authority, `app/research/persistence/lifecycle.py`) answers "queued/running **and** the lease exists". Consequences: a worker that dies mid-process reads `interrupted` within the lease TTL instead of falsely `running` until the 24 h state TTL; an expired lease cannot be renewed back into existence, so liveness never flips back on mid-flight; a legitimately slow silent unit of work must stay well under the TTL (emits and cancel checks renew it).
2. **The startup sweep stays.** `fail_jobs_without_a_worker` still closes every queued/running job at boot — a restart takes every thread with it regardless of any lease — and now deletes the dead workers' leases too.
3. **A resumed Recency launch is a new job id bound to the old launch record** — the Grid Search / Walk-Forward Finish shape. `POST /api/jobs-internal/recency-chart` accepts `resume_launch_id`; the spec fields it carries are ignored (the stored `ConfigJson` governs, re-validated at resume); the router refuses (409 `NOT_RESUMABLE`) a completed launch, a still-live one (asked of the lease only when the row says `RUNNING`), or a deleted one, and the worker's first act is the attempt-fence claim, which binds the record to the new job id. A redelivery of a *closed* job under its original id still answers 409 — the four hazards stay avoided by never replaying a transport record.
4. **Recency joins the attempt fence (ADR 0055 §4).** `RecencyLaunches` gains `Attempt` / `JobId` / `Incomplete` / `FailureReason` (schema version 9); the fence contract in `app/research/persistence/fence.py` is parameterized by column names and status vocabulary so the PascalCase table claims through the same code. Every launch write — per-run snapshot and terminal status — is fenced: a worker whose generation moved on (a resume claimed the launch) cannot write over it. Every launch claims, fresh ones included, so the fence is uniform.
5. **Terminal accounting comes from the durable record, never the replay.** The worker no longer overwrites `SucceededRuns` with its execution's success count: the per-persist increments stand (passing `None` keeps them), while `FailedRuns` remains this execution's count — failed runs leave no durable trace, so a resume re-ran every one of them. A previously-failed launch whose recorded cells are skipped therefore reconciles to `COMPLETED` instead of falsely failing.
6. **Cancelled launches are resumable** (owner decision, matching grid/walk-forward claimable statuses): anything not `COMPLETED` and not still live may Finish. There is no auto-resume; resume is an explicit operator act.
7. **Python only.** No .NET change: .NET stays the transport that mints job ids, writes initial state and serves SSE; a resume rides the same `startJob` path as any launch, so the drawer follows the new id and the new event stream. This keeps the issue aligned with the owner's direction of shrinking the .NET surface without coupling the two efforts.

## Considered options

- **Heartbeat thread for lease renewal.** Rejected in Decision 1: it proves the *process* is alive, not the worker, so a hung worker would still read live.
- **Reset `cancel_requested` and restart a worker under the original job id.** The #1937 investigation tried and removed exactly this: the event stream, result key, TTL discipline and launch accounting all still describe the first execution, and the UI closes its stream on the first historical terminal event it replays. A new job id per execution avoids all four hazards structurally; it is Decision 3.
- **Resume by relaunching a fresh launch id** (the ADR 0057 cutover answer). Kept for `COMPLETED`-adjacent cases and as the fallback when code identity changed — but it discards the launch's evidence continuity and re-runs recorded cells, which the durable per-run rows make unnecessary.
- **Persist failed runs durably** (so `FailedRuns` could also be read back from the record). Deferred: with resume re-running everything not recorded, the final execution's failures *are* the launch's failures; the extra table column buys nothing this contract needs.

## Consequences

- A hung worker (stuck mid-cell past the lease TTL) reads `interrupted` while its thread still exists; a resume claimed concurrently is kept correct by the attempt fence, and the stale writer's writes are refused. The record stays truthful either way.
- Jobs that go silent longer than the lease TTL without emitting or checking cancellation would read `interrupted` while alive — today every research job checks cancellation per cell and emits per run; the contract docstring (`app/jobs/__init__.py`) states the obligation for future job types.
- The launches list (`GET /api/research/recency/launches`) is the first reader of `RecencyLaunches.Status`; presentation follows the shared rule (`running` + not live → `interrupted`) with lowercase vocabulary.
