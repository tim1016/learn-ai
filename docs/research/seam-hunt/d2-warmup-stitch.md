# D2: where warmup history meets the first live minute

- **Ticket:** #2279 (map #2276, seam D2)
- **Baseline:** every `file:line` below is at `a14f1df143b67aad672949b5922f9aef68e740aa` (master, 2026-09-23). Paths are relative to `PythonDataService/` unless they start with `docs/`.
- **Method:** static trace of the code. There was also one in-process probe: a scratch script, not committed, that drove `strategy_evaluations` with a fake feed. No IB Gateway, Alpaca, Polygon or containers were touched.
- **Verdict:** **charted hazard, with one proven defect.** The representation contract holds: bar-close labels, `int64 ms UTC`, no forward-fill, and overlap is rejected rather than deduplicated. The *stitch* is not guarded. A warmup bucket that the replay left unfired is decided later by the live loop, under the mode captured at warmup (`DECIDE`), with no check on its age. This happens even when the run is paused (**G4, proven, bug filed**). Separately, minutes can be missing between the last warmup minute and the first live minute, and nothing reports it (G1, G5).

## 0. Correcting the ticket's premise

The ticket says warmup comes from "lake/Polygon history". **It does not.** The live paths warm from one of two sources:

1. **A fresh instance, whose ledger is empty:** IBKR's historical endpoint. `_RetainedSourceBarFeed.recent_closed_bars` calls `IbkrMarketDataFeed.recent_closed_bars` (`app/services/bot_trade_strategy.py:320-325`). That function calls `fetch_historical_minute_bars` (`app/marketdata/ibkr_feed.py:342-347`), which uses `reqHistoricalDataAsync` for `TRADES` bars with `keepUpToDate=False` (`app/broker/ibkr/bars.py:592-602`).
2. **An instance that has already run (any Resume or restart):** the instance's own **retained source-bar ledger**, and nothing else (`app/services/bot_trade_strategy.py:292-319`).

A Polygon-backed `recent_closed_bars` exists only in the qualification harness (`app/broker/alpaca/clerk/sqlite/qualification_polygon_replay.py:112`), not on the live path. So "can adjusted and unadjusted prices mix?" is really a question about IBKR history vs IBKR real-time bars, and about the retained ledger across a corporate action (G6).

## 2. Invariants each side assumes of the other

| # | Assumption | Held by | Guaranteed? |
|---|---|---|---|
| I1 | Both sides label a minute `[start, start+60s)`, with `end_ms` = close. | Both | **Yes.** History: `bars.py:626-629`. Live: `minute_assembler.py:163-167`. Port contract: `app/marketdata/feed.py:92-103`. |
| I2 | Both sides are `int64 ms UTC`, with no ISO strings or naive datetimes. | Both | **Yes.** `_to_utc_ms` rejects a naive datetime and parses IBKR strings through `America/New_York` (`minute_assembler.py:77-97`). `formatDate=2` requests epoch time (`bars.py:600`). |
| I3 | Session phase is labelled the same way on both sides. | Session filter | **Yes.** Both use `_session_phase_for_ms(start_ms)`, which goes through `session_authority` (`bars.py:638`; `minute_assembler.py:104-106`, `:176`). |
| I4 | No minute is in both history and live. | Ledger, strategy | **Enforced by refusal, not by construction.** `requested_at_ms` cuts off the forming minute (`ibkr_feed.py:365`). If one slips through, the live `append` sees the same identity with a different payload (`provenance` differs: `source_bar_ledger.py:774-781`) and raises `SOURCE_BAR_IDENTITY_CONFLICT` (`:602-607`). This is fail-closed: no dedup and no double count. See G3 for how an overlap can still happen. |
| I5 | No minute falls between history and live. | Strategy, consolidator | **Not guaranteed, and not detected.** The seal declares `gap_policy="tolerated_not_filled"` (`app/schemas/signal_program_seal.py:128`, `:140-148`). The ledger checks monotonicity only (`source_bar_ledger.py:629-633`). `ContinuityLoop` scans for missed windows only after an interruption has been recorded (`ibkr_continuity.py:169-170`). A pre-first-delivery gap never records one (`:209-214`). See G1 and G5. |
| I6 | The first live minute is complete. | Strategy | **No, by design** (ADR 0053 §13, ruling R2). Charted hazard G2. |
| I7 | Every bucket the live loop evaluates closed *live*, and its mode reflects the run's gate when it closed. | `run_trade_bot` pause/liveness handling | **No: proven violated (G4).** A bucket that closed in warmup but was never fired carries the warmup's `DECIDE` (`bot_trade_strategy_warmup.py:154`; `signal_program.py:319-326`). It is decided by the first live bar, however old it is and whether or not the run is paused. |
| I8 | Warmup covers the sealed lookback, ending just before the live stream. | Seal (`warmup_lookback_days`) | **Only for a fresh instance.** A resumed instance replays the whole retained ledger, which can hold up to `SOURCE_BAR_STREAM_CAPACITY = 200_000` bars (`source_bar_ledger.py:40`). That history ends where the previous run stopped, not "now" (G5). |
| I9 | History and live prices are on the same adjustment basis. | Indicators | **Unverified.** Fresh: IBKR `TRADES` history and real-time bars. Resumed: raw retained rows that may predate a split (G6). |
| I10 | Warmup succeeded. | Strategy readiness | **Not surfaced.** A fetch failure returns `[]`, and the only record is a warning log (`ibkr_feed.py:348-358`, and the port contract at `feed.py:360-361`). The run starts cold. |

## 3. Named suspected gaps

Severity follows the map: P0 = can place, duplicate or fail to cancel a real order; P1 = a gate fails open or false live state; P2 = wrong but self-correcting, or diagnostic-only; P3 = imprecise.

1. **G1 STITCH-GAP-DURING-FETCH (P2).** *Hypothesis:* a minute that closes after `requested_at_ms` (`ibkr_feed.py:340`) but before the first 5-second bar of the new subscription is in neither side. That window covers the IBKR historical fetch, `_HISTORICAL_BARS_TIMEOUT_S`, and the warmup replay (`bot_trade_strategy.py:564-578`). The ledger accepts the jump, and no continuity event is recorded. If the missing minute is inside a bucket, the bucket is decided without it. If it is the bucket's last minute, the bucket's `end_ms` is short and `advance` quarantines it as `TIMEFRAME_MISMATCH` (`signal_program.py:196-197`), so that decision is lost. *Prototype:* a fake `IbkrClient` whose `reqHistoricalDataAsync` sleeps across a minute boundary. Drive `_RetainedSourceBarFeed` and `_signal_strategy_evaluations`, then assert on the missing identity, the absence of any continuity event, and the quarantine when the missing minute ends a bucket.
2. **G2 SHORT-FIRST-LIVE-MINUTE (P2, *charted hazard*: ADR 0053 §13 / ruling R2, `ibkr_continuity.py:114-116`).** *Hypothesis:* the first live minute holds fewer than 12 contributions but is delivered as `realtime` with full decision weight. Its open, high, low and volume go into the stitched bucket. Close-only indicators such as EMA are unaffected. High/low/volume indicators such as ADX and RSI-range are affected. The ADR explicitly defers "deferring a new consumer's first emitted minute" as a change to *this* seam. *Prototype:* a feed with a mid-minute subscription (3 of 12 contributions). Compare a high/low-driven program's bucket against the complete-minute reference.
3. **G3 FIRST-LIVE-BAR-OVERLAPS-LAST-HISTORY-MINUTE (P2, fail-closed).** *Hypothesis:* the live stream's first minute can have the same identity as the last history minute. There are two routes. (a) The host clock runs ahead of IBKR, so a still-forming bar passes `end_ms <= requested_at_ms`. (b) A fresh `reqRealTimeBars` delivers first a 5-second bar stamped before the subscription (bar-start labelling) that falls inside a minute history already returned as closed. Either way, the first `ledger.append` raises `SOURCE_BAR_IDENTITY_CONFLICT` (`source_bar_ledger.py:602-607`) and the run dies at start. This is the same shape as the fleet crash on 2026-08-25 that `ibkr_feed.py:360-365` fixed for the forming bar. *Prototype:* a fake clock offset of +2 s against the fake IBKR history, plus a recorded IBKR first-bar timestamp relative to the subscription time. Needs a recorded real-time-bar capture (paper).
4. **G4 STRANDED-WARMUP-TAIL-BUCKET (proven, see §4; P1, candidate P0; bug #2303).**
5. **G5 RESUME-RETAINED-GAP (P2; the owner may rate it higher because it changes which real orders are placed).** *Hypothesis:* a resumed instance warms only on its retained ledger (`bot_trade_strategy.py:292-319`). That ledger ends when the previous run stopped, so every minute from then until the first live bar is missing and nothing reports it. The gap can be hours to days, for example stopped at 11:00 and resumed the next morning. Indicators run straight across the hole, so a resumed instance holds different indicator state from a fresh deploy of the same program at the same instant. The replay length is also unbounded (up to 200k rows, `source_bar_ledger.py:40`), which delays the subscription and widens G1. *Prototype:* seed a temp ledger with day-1 bars through 11:00, then resume with day-2 live bars. Compare indicator state and decisions against a fresh-instance warmup over the same true history, and time the replay at full ledger capacity.
6. **G6 RESUME-ADJUSTMENT-MIX (P3).** *Hypothesis:* retained rows are the raw observations of the day. After a split, a resumed instance replays pre-split raw bars and then post-split live bars, a price discontinuity the strategy reads as a real move. A fresh deploy would use IBKR history, which is presumably split-adjusted. *Prototype:* a synthetic 2:1 split between retained and live bars. Needs paper confirmation of IBKR's `TRADES` adjustment semantics for the fresh path.
7. **G7 LOOKBACK-UNITS (P3).** *Hypothesis:* the seal's `warmup_lookback_days` is documented as **calendar** days (`bot_trade_strategy_warmup.py:36-54`), but it goes to IBKR as `"{N} D"` (`ibkr_feed.py:345`). If IBKR counts that as trading sessions, warmup is longer than sealed. If it counts calendar days, a Monday deploy with 5 D gets about 3 sessions. In both cases the sealed number is not what the bot warms on. *Prototype:* the paper IBKR history response for `5 D` on a Monday (count distinct sessions). Needs paper.
8. **G8 SILENT-COLD-START (P2).** *Hypothesis:* when warmup fails (`ibkr_feed.py:348-358`), the run starts with no history, and the only record is one log line. Whether a program then decides on unwarmed indicators depends on each program's `decision.ready`. That gate has not been verified for every registered program. *Prototype:* for every key from `supported_alpaca_paper_strategy_keys()`, give an empty warmup and live bars. Assert that no intent appears before `warmup_bars` consolidated bars.

**Cleared (static):** bar-close labelling (I1), `int64 ms UTC` on both sides (I2), session-phase agreement (I3), and no forward-fill or dedup-by-repair anywhere on the path. An overlap is refused, not merged (I4).

## 4. Proven by reading (and confirmed by an in-process probe)

### G4: a warmup bucket left unfired is decided live, stale, and even when paused

1. The warmup replay feeds each bar through `consolidator.update` only (`bot_trade_strategy.py:491-496`, called from `bot_trade_strategy_warmup.py:154`). It never calls `scan`, so the final bucket stays in `_working` even when it is already full width (`trade_bar_consolidator.py:84-134`, `:154-171`).
2. Each warmup source bar's mode is recorded as **DECIDE** in `SignalProgram._captured_modes_by_close_ms` (`bot_trade_strategy_warmup.py:154` → `signal_program.py:317-322`).
3. The first live bar to be evaluated fires that bucket (`trade_bar_consolidator.py:102-107`). `on_consolidated_bar` pops the **warmup-captured** mode for the bucket's close (`signal_program.py:326`) and not the mode the live `PauseAwareFeed` captured (`bot_runtime.py:74-77`). `advance` checks only the width and `end_ms > last` (`signal_program.py:196-199`).
4. `_evaluation_from_active_stage` produces a `StrategyEvaluation` with `evaluation_mode=DECIDE` and `decision_bar_close_ms` = the bucket's warmup close (`bot_trade_strategy.py:622-638`). `run_trade_bot` discards only `OBSERVE_ONLY` (`:864-873`). An ENTER passes the liveness gate evaluated at *now* (`:880-909`) and reaches `clerk.execute_for_instance` (`:925-936`). Nothing on the path compares `decision_bar_close_ms` with the current time. `admit_on_delivery` bounds lateness only for non-`realtime` source bars (`feed_continuity_policy.py:77-81`), and nothing in `app/broker/alpaca/clerk` reads `decision_bar_close_ms` except to write evidence (`clerk/sqlite/runtime.py:933`, `:1530`).

**When it is reached.** Whenever warmup ends on a full-width bucket. That is every start or resume after the decision session's last bucket has closed, which includes any deploy in the evening, overnight or pre-market. It also happens at a bucket boundary mid-session, where it is benign because the bucket is at most about a minute stale. The session-close force-flush exists to stop exactly this stranding, but it is only in the live loop (`bot_trade_strategy.py:584-596`).

**Consequences.**
- **Stale decision.** The previous session's final bucket is decided at the next session's first bar, possibly days later over a weekend. An always-on run decides the same bucket at the close, through the force-flush, where an RTH ENTER meets a closed market at the liveness gate. The deploy time therefore changes whether a real order is placed. For an extended-session run, the leg is priced as a marketable limit anchored to that stale bar's close (`clerk/program_leg.py:500-516`).
- **Pause fails open.** Pause clears the run gate so that every later candidate is `OBSERVE_ONLY` (`bot_runner.py:1166-1170`). The stranded bucket ignores the gate. An instance paused overnight after an evening deploy still sends that bucket's ENTER or EXIT to the Clerk at the next open.
- **FR-016 bypass on Resume.** The stranded bucket is staged in the live loop, not in the replay, so the `captured_decisions` lookup (`bot_trade_strategy_warmup.py:156-167`) never sees it. The same `evaluation_id` that an earlier run already decided at its close is decided again. ENTER idempotency on `(instance, decision_id)` (`clerk/sqlite/enter.py:137-155`, `:260-275`) stops a duplicate order only when the first decision *created* a command. A first decision that was blocked or had no action leaves nothing to collide with.

**Probe (scratch, not committed).** This drove `strategy_evaluations` for `ema_crossover_signal` with RTH history for 2026-09-17, 18 and 21 and one live bar at 09:30 on Tuesday 2026-09-22. It yielded one evaluation, with `decision_bar_close_ms` = 16:00 ET on Monday 2026-09-21 and mode `DECIDE`. Wrapped in a **paused** `PauseAwareFeed` (`observe_only=True`), the same bucket was yielded again with mode **DECIDE**. The probe did not produce an ENTER, because the synthetic prices were intent-free. Everything after the evaluation is the unconditional code path cited in step 4.

**Severity: P1, candidate P0.** A gate fails open (pause, and decision lateness), and the worst reachable consequence is a real ENTER or EXIT order that the operator's Pause or an always-on run would not have produced. **Filed as #2303.**

## 5. What the prototypes need (sandbox notes)

- G1, G2, G4, G5 and G8 run fully in-process: a fake `MarketDataFeed` or `IbkrClient`, a temp `SourceBarLedger`, and `strategy_evaluations` or `run_trade_bot` with `_FakeClerk` (`tests/_helpers/bot_runner/doubles.py`). The fakes must keep **provenance** distinct (`history` vs `realtime`), because the ledger's conflict rule depends on it.
- G3, G6 and G7 each need one recorded paper IBKR fact: the timestamp of the first real-time bar relative to the subscription, the adjustment basis of `TRADES` history, and what `N D` means for 1-minute bars. Record these as fixtures and never call IBKR live from a test.
