### F01 — P1 / #1927: removing EF entities can delete the very evidence being preserved

**Classification:** Missing migration contract. Direct persistent-data-loss risk.

The Solution removes the four Recency entities and EF registrations while preserving their tables in place. Removing an EF model entity is not, by itself, a transfer of schema ownership.

**Failure:** Populated Recency tables → remove the registrations → generate the ordinary next EF migration → migration contains table drops → backend startup applies it → historical evidence disappears.

The current four mappings are in [AppDbContext.cs:247](/Users/inkant/learn-ai/Backend/Data/AppDbContext.cs:247), including cascading foreign keys and unique fingerprint/membership indexes. Backend startup invokes migration at [Program.cs:224](/Users/inkant/learn-ai/Backend/Program.cs:224), reaching [DatabaseInitializer.cs:27](/Users/inkant/learn-ai/Backend/Data/DatabaseInitializer.cs:27).

The project pins EF design tooling 10.0.2 in [Backend.csproj:18](/Users/inkant/learn-ai/Backend/Backend.csproj:18). Its official [MigrationsModelDiffer source](https://github.com/dotnet/efcore/blob/v10.0.2/src/EFCore.Relational/Migrations/Internal/MigrationsModelDiffer.cs) emits DropTableOperation when removing a table unless the source mapping is excluded from migrations. Microsoft documents [migration exclusion separately from model exclusion](https://learn.microsoft.com/en-us/ef/core/modeling/entity-types#excluding-from-migrations).

**Required correction:** Specify a non-dropping schema-adoption protocol, including migration history/snapshot treatment, Python baseline ownership, deployment order, and rollback. “Do not drop data” is a requirement, not the mechanism that satisfies it. Do not simply hand-edit the model snapshot.

**Acceptance:** Upgrade a populated database; build a fresh database; apply a later unrelated EF migration; exercise the declared rollback. Verify row identities, values, foreign keys, indexes, and sequences survive. Inspect generated SQL for Recency drops. A correctly designed handoff closes this finding; data loss is not inevitable.

**Failure:** Worker A loses its Redis record but remains alive → the study appears interrupted → Finish starts B → B fills missing rows and completes → A resumes and overwrites those same keys or status. If deletion waits only for B, A can still attempt writes after acknowledged deletion.
