**Answer.** Counting answer-producing implementation units rather than call sites, transports, SQL readers, validators, or display predicates, the pinned tree has **eight backend implementations** in the Alpaca scope: three P&L implementations (the shared FIFO lot engine, Gallery's null-safe day-P&L aggregate, and C3 broker-versus-local reconciliation) and five exposure/position implementations (the normalized execution fold, the legacy JSONL account projection/delta pipeline, the legacy incremental rollup mirror, the SQLite attributed-position fold, and SQLite broker-minus-attributed reconciliation). The apparent FIFO proliferation is mostly refuted: SQLite economics, panel/catalog services, routers, and Angular delegate or pass values through. The surviving authority defect is instead the meaning of *flat*: the registered SQLite rule treats `abs(qty) >= 1e-9` as exposure, while the rollup removes exactly `1e-9`, active SQLite panel/catalog reads surface every nonzero residue, and Angular's deploy guard uses exact zero. The rollup calls the canonical FIFO primitives for P&L but independently folds exposure, and its cited tests do not compare that mirror with the named canonical at the boundary. Confidence is **high** for the static call graph and formulas at the pinned SHA, and **medium-high** for runtime reachability because activation selects mutually exclusive JSONL and SQLite paths and this audit did not exercise a live broker account.

This is a point-in-time audit and therefore supporting evidence, not an implementation authority. That register follows [`docs/doc-authority.md`](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/doc-authority.md#L13-L17): `docs/math-sources-of-truth.md`, the engine map, ADRs, code, and focused tests retain their existing roles.

## Counting rule and scope

An **implementation unit** here is a cohesive formula pipeline at one site that authors an Alpaca product or proof answer. A file that only normalizes inputs, selects the active authority, calls a named primitive, maps a response, or formats a value is an adapter and does not increment the count. SQL `SUM`, integrity comparisons, closing-order derivations, and flat/nonflat predicates are inventoried because they can affect a numerical consumer, but are labelled **derived/validator** rather than promoted to separate owners of the underlying position or P&L. This keeps the count reproducible instead of counting every helper or function call as a new engine.

The activation seam matters. The engine map says a missing fence selects legacy JSONL, a valid fence selects SQLite, and an invalid/failed selection fails closed; it also says the two paths do not mix in active-SQLite product reads ([authority map](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/engine-authority-map.md#L19-L21), [legacy boundary](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/engine-authority-map.md#L48-L48)). I therefore count mutually exclusive legacy and SQLite formulas separately, but do not describe them as concurrently writing one account. ADR 0035 itself is **Accepted**, despite the stale “proposed” label in the doc index ([ADR status](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/adrs/0035-alpaca-clerk-sqlite-event-sourced-authority.md#L1-L20)).

## Surviving findings after adversarial refutation

### 1. FIFO is singular; exposure is not

The SQLite reader's incremental cache calls `apply_fill_to_lots`, then calls `compute_open_pnl` and `realized_pnl_for_window`; the legacy rollup calls those same primitives. Neither reimplements `(exit - entry) * quantity` or mark-to-market lot math. C2's extra `sum(...)` calls aggregate canonical closed-lot rows and fees; they are not another lot matcher. I found no `.NET` or Angular FIFO computation in the Alpaca path. This supports the register's statement that one Python FIFO implementation serves both selected authorities ([registered FIFO](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/math-sources-of-truth.md#L97-L98)).

Exposure has one intentional same-answer mirror: `rollup_cache._apply_fill_delta` independently deduplicates and folds signed fill quantities for O(1) reads. Its module prose calls `exposure.py::project_instance_exposure` canonical, but its test only checks ordinary expected quantities and does not invoke the canonical fold. The direct adapter parity test covers `exposure.py` against `fold_execution_exposure`; it does not cover the rollup. Therefore the mirror's claimed parity receipt is absent.

### 2. “Flat” has incompatible boundary implementations

The registered active-SQLite predicate is inclusive: `abs(qty) >= 1e-9` is nonzero. Four consumer families disagree:

| Path | Effective rule | Consequence |
|---|---|---|
| SQLite custody/reconcile/recovery | nonzero when `abs(qty) >= 1e-9` | Exactly `1e-9` is exposure. |
| Legacy rollup | delete when `abs(updated) <= 1e-9` | Exactly `1e-9` is flat, contradicting the inclusive predicate. |
| SQLite economics/panel/catalog/presentation | SQL `attributed_qty != 0`, Python `abs(qty) > 0` | Any representable residue below `1e-9` can render as exposure, alter health copy, or say off-duty-with-exposure even though custody/recovery treats it flat. |
| Angular deploy guard/label | `Number(qty) === 0` / `qty !== 0` | Any nonzero broker quantity blocks the Reference-parity option; no shared tolerance contract is applied. |

This is read-confirmed, not hypothetical reachability: SQLite `positions` adds floating deltas without deleting sub-epsilon rows ([fold write](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/broker/alpaca/clerk/sqlite/folds.py#L812-L840)), the raw projection returns every row ([projection read](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/broker/alpaca/clerk/sqlite/projections.py#L642-L649)), and the active panel adapter applies the bare-zero filter. I did not produce a live-account residue, so the frequency and user impact remain unmeasured.

There is a related internal boundary discrepancy in the economic reader: C2 position coverage requires `abs(delta) < 1e-9`, while `_assert_effective_fills_match_positions` uses `math.isclose(..., abs_tol=1e-9)`, which accepts equality at exactly `1e-9` ([C2 coverage](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/broker/alpaca/clerk/sqlite/economic_projection.py#L471-L481), [integrity check](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/broker/alpaca/clerk/sqlite/economic_projection.py#L1223-L1247)). That does not author a second position, but it means two SQLite proof gates give different answers at the canonical boundary.

## Adversarial refutations

I made a second pass specifically to disprove the candidate duplicates. These candidates did not survive:

1. **`fills.py` as FIFO/P&L.** It validates ownership, namespaces, execution identity, and field presence, then creates sorted `FillRecord`s. It performs no lot matching, P&L, or exposure sum.
2. **`sqlite/facts.py` as economic math.** Its math imports support finite-value validation of typed transition facts. It neither folds positions nor calculates P&L.
3. **`sqlite/economic_projection.py` as a second FIFO engine.** Its cache stores canonical FIFO state and calls the canonical lot mutation. Its independent arithmetic is aggregation, fee fidelity, and fail-closed quantity comparison—not FIFO matching.
4. **`execution_coverage.py::position_delta` as account position.** The value proves that two execution-evidence representations can replace one another without changing quantity. It never writes or reports current account inventory.
5. **P&L attribution service and router as calculators.** The service selects active SQLite and owns reader lifetime; the router validates the time window and maps errors. Both return the economic reader's result unchanged.
6. **Panel/catalog services as P&L engines.** They select legacy versus SQLite and copy `realized_pnl_today`/`open_pnl`. Gallery alone adds the separately named presentation total.
7. **Angular Gallery as P&L/session-return authority.** The tile reads both server fields. `* 100` converts a fractional return to percent display units and does not rederive the return; no realized-plus-open expression remains.
8. **Angular Account Desk as C2/C3 authority.** It renders the bundled proof. Its chart's `/ 1_000` is a time-unit conversion required by the chart library, not P&L arithmetic.
9. **`LiveEngine` as Alpaca P&L.** The cited method serializes `trade.pnl_pts`; it does not calculate it, and current Alpaca paper execution is a different entry point. `LiveEngine` remains relevant to IBKR/offline replay, not this product census.
10. **`broker/ibkr/pnl.py` as a duplicate.** It copies broker-authored IBKR fields into a wire model. It is neither arithmetic nor an Alpaca runtime dependency.
11. **The .NET portfolio lot engine as Alpaca Broker V2 FIFO.** It owns the separate EF/Postgres portfolio domain, with different fills and consumers. No current Alpaca panel, Gallery, or C2/C3 route calls it, so it is parallel scope rather than a comparable Alpaca answer.

## Confidence and unanswered questions

- **High confidence:** formulas, direct callers, tests, and the absence of Alpaca P&L arithmetic in Angular/.NET at the pinned commit. Searches covered the named issue sites plus their direct position, projection, panel, router, and Frontend consumers.
- **High confidence:** the exact-boundary disagreements. They are literal `>=`, `<=`, `<`, `math.isclose`, `!= 0`, and `=== 0` branches, and no cross-boundary parity test covers the rollup, active panel adapter, or Angular deploy guard.
- **Medium-high confidence:** “who consumes each.” Static call graphs and authority-selection docs agree, but no live broker/UI run was used to prove every deployed configuration.
- **Unmeasured:** whether an active account currently contains a sub-epsilon persisted position; the census proves the code can classify such a value inconsistently, not that one exists in production data.
- **Deliberately unresolved:** which flatness rule should win outside the already-registered SQLite custody predicate, and whether the legacy rollup should remain a mirror. Those are repair/authority decisions for a downstream ticket, not this fact-finding audit.
