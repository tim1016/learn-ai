# State-writer census — bot lifecycle and deploy

**Question:** Who writes bot lifecycle duty state, and who writes deploy state — and how many writers are there really?

**Commit read:** [`e7325d2ff0a122ffde3418cac94aa2f872f10ffa`](https://github.com/tim1016/learn-ai/tree/e7325d2ff0a122ffde3418cac94aa2f872f10ffa)

**Date:** 2026-08-17

**Answer:** There is no repository-wide single writer for either phrase. For duty state, `BotLifecycleEvaluator` is the sole lifecycle-specific owner of `lifecycle_dispositions.jsonl`, but it is not the sole caller allowed to change the state that log is meant to govern: four production command modules call the `lifecycle_state.json` mutation seam, four call the `desired_state.json` seam, and five unique command modules do one or both; the shared repository module is an additional storage layer on each write stack. Those repositories serialize each individual file with an advisory lock, but the non-evaluator paths do not take the lifecycle operation fence, do not write evaluator dispositions, and carry neither an owner generation nor a TTL. “Deploy state” names four different durable families: the canonical Alpaca Clerk's SQLite registration/run folds, the in-process runner's JSON instance/run records, the deprecated host-runner's `run_ledger.json`, and the IBKR-lineage account binding state (`DEPLOYED` / `ACTIVE` / `RETIRED`). Each family has a narrow storage writer, but the account-binding writer has several policy entry points, and neither the Alpaca multi-artifact launch nor the host-runner multi-artifact deploy is one atomic commit. Confidence is high for the direct-writer inventory and artifact-level fencing, and medium for the product meaning of the words “deploy state” because the code uses them for these distinct machines rather than declaring one aggregate deploy record.

This is point-in-time supporting evidence, not implementation authority. Per the [Docs Authority Index](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/doc-authority.md#L1-L16), the accepted ADRs and current code own decisions and behavior; this audit reports their present agreement and disagreement.

## Scope and counting rules

The census covers production Python modules that either contain the duty/deploy vocabularies, call a durable mutation seam, or sit on the request-to-storage call paths named in issue #1591. The phase-literal sweep (`OFF_DUTY`, `ON_DUTY`, `RETIRED`) was classified in full; modules whose match belongs to account binding or a separate evidence domain are grouped explicitly rather than silently dropped. Test fixtures and developer-only synthetic qualification writers are excluded from the writer count, but tests are used as evidence. A **writer** is a module that directly mutates an artifact or deliberately invokes its owning writer as part of a command. A **projection** derives a view without persisting the classified state. A **reader** consumes or transports state without deriving a new classified state. “Direct writer” below means the module reaches the storage repository mutator; it does not mean it alone decides policy.

The issue combines several homonyms, so counts are artifact-specific. For the duty files, this summary counts production command modules that invoke the domain mutator; the following core table separately names the repository/storage module that publishes the bytes. For deploy artifacts, where a single numeric total would conflate distinct state machines, the summary names the storage seam and whether it has multiple policy entry points.

“None” in the fencing column means no owner generation or expiring lease/TTL. It does **not** mean unsafe partial-file writes: the JSON repositories generally use advisory locks, fsync, and atomic rename. That distinction matters because serialization prevents torn same-file writes but does not fence a stale authority or make a multi-file transition atomic.

## Overlapping writers and read-modify-write risks

### 1. Duty phase and desired intent have bypass writers

The accepted ADR says the evaluator is the only durable writer of phase, roster, and desired-state control intent ([ADR-0026 amendment](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/adrs/0026-daily-bot-lifecycle-three-state-button-rule-single-writer.md#L15-L22), [single-writer decision](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/adrs/0026-daily-bot-lifecycle-three-state-button-rule-single-writer.md#L119-L132)). The code does not meet that statement. `BotTaskRegistry` writes both files directly; boot recovery writes both directly; terminal recording writes desired state directly and reaches lifecycle state through `BotRunEvidenceService`; `BotRunEvidenceService` writes lifecycle state directly. Those paths omit evaluator receipt IDs, so their resulting records either preserve an older `last_disposition_id` or have none.

The shared repository flocks prevent two processes from reading the same version and simultaneously replacing the same file. They do **not** prevent a semantically stale writer from committing after another authority, because no owner generation or compare-and-swap token is checked. More importantly, the direct paths do not hold `lifecycle_operation_fence`, so multi-file sequences can interleave with evaluator transitions. This is a read-modify-write authority risk, not a torn-JSON risk.

The existing “one mutating owner” test does not disprove this finding. Its AST visitor recognizes only repositories assigned from direct constructor calls and direct constructor-call receivers ([test visitor](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/tests/engine/live/test_bot_lifecycle_evaluator.py#L35-L79)); it then scans all production modules and expects no violations ([test assertion](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/tests/engine/live/test_bot_lifecycle_evaluator.py#L97-L112)). Calls such as `self._desired_repo(...).set(...)`, `self._lifecycle_repo(...).set_phase(...)`, and mutators reached through injected repository callables fall outside that recognition logic. The test therefore passes while the direct writers above remain.

### 2. Canonical Alpaca deploy has two durable semantic copies and a third duty copy

For a paper-trade launch, the runner first registers immutable strategy/run identity with the active SQLite Clerk, then records runner JSON, then writes desired and lifecycle state, then installs the task ([activation order](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/services/bot_runner.py#L440-L497)). SQLite is the product authority for activated Alpaca paper accounts under [ADR-0035](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/docs/architecture/adrs/0035-alpaca-clerk-sqlite-event-sourced-authority.md#L1-L16), while the JSON instance/run artifacts remain the process runner's restoration/evidence store. They do not race on the same bytes, but they overlap on strategy configuration and active run identity.

SQLite registration is strongly fenced and transactional inside its own authority. There is no cross-store transaction or durable launch coordinator spanning SQLite registration, runner JSON, desired state, and lifecycle state. A failure after SQLite registration can therefore leave a registered bot/run without matching runner launch state; a failure after `current_run.json` can leave the pointer advanced before duty state is `ON_DUTY`. Existing quarantine/boot-recovery code can detect some inconsistent shapes, but detection is not atomicity.

Dry-run and log-only deployments skip SQLite registration entirely and rely on runner JSON plus duty state, so the writer set also varies by execution mode.

### 3. Deprecated host deploy is a multi-artifact workflow, not one deploy record

The host deployment path holds the per-SID lifecycle operation fence while it writes the content-addressed run ledger, optionally reopens a retired lifecycle, and records a `DEPLOYED` account binding ([workflow](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/engine/live/host_daemon.py#L1304-L1321)). The fence prevents another lifecycle operation from interleaving, but it does not make the files transactional. A run ledger written before a later lifecycle/binding failure remains durable, and the method has no rollback or PENDING deploy transaction. This is compatibility-only IBKR lineage under the repository's deprecation rules, not a model for Alpaca Broker V2.

### 4. Account binding state has one generic storage seam but multiple policy owners

The normal daemon path is well bounded: host capability plus current Clerk generation, then the account intake lock, then the binding writer. The storage writer appends the command ledger first and the compatibility registry second; if the second write fails, parity becomes observably dirty rather than silently clean ([dual-write contract](https://github.com/tim1016/learn-ai/blob/e7325d2ff0a122ffde3418cac94aa2f872f10ffa/PythonDataService/app/engine/live/account_binding_ledger.py#L129-L148)).

It is nevertheless not true that the Clerk is the only code capable of a binding decision. `run.py` can write an `ACTIVE` compatibility transition; lifecycle retirement writes `RETIRED`; false-crash repair and soft-delete retirement append corrected `RETIRED` rows; proposal folding and ledger baseline are maintenance writers. They share account-ledger serialization but not a common authority generation. The specialized direct paths validate their narrow transition shapes, which reduces misuse; it does not turn them into the same writer owner.

### 5. No TTL fences protect duty or filesystem deploy writers

The per-SID lifecycle lock and artifact locks are advisory process-held flocks. The deprecated deploy lock is a mkdir claim with a 30-second wait but no lease expiry or owner generation. The JSON runner pointer likewise has no owner generation. Only SQLite Clerk deploy/run registration combines authority generation, a durable execution lease TTL, a prepared revision-bound admission snapshot, and database serialization. “Fenced” should therefore be qualified by artifact; a lock is not the same as a stale-writer fence.

## Adversarial refutation log

The following candidates were investigated and rejected:

1. **Candidate: the ADR is accurate because only `bot_lifecycle_evaluator.py` calls the state mutators. Refuted.** Direct production calls exist in `bot_runner.py`, `bot_boot_recovery.py`, `bot_run_evidence.py`, and `bot_run_terminal.py`. The evaluator is unique only for the disposition log.
2. **Candidate: the single-writer contract test catches those direct calls, so the apparent bypasses must be test-only or unreachable. Refuted.** The visitor does not resolve repository factories or injected callables. The bypasses are wired into `BotTaskRegistry` construction and its deploy/stop/boot paths.
3. **Candidate: `host_daemon.py` is a second direct duty-phase writer. Refuted.** It reads the repo for admission, but duty transitions and lifecycle reopen flow through `BotLifecycleEvaluator`; terminal finalization also delegates to the evaluator.
4. **Candidate: `paper_deploy_service.py` writes deploy state because it creates a `status="deployed"` receipt. Refuted.** The module declares itself pure, returns Pydantic views/receipts, and opens no durable store. The receipt is not persisted by that service.
5. **Candidate: the three state literals in `broker/v2panel/vocabulary.py` create another lifecycle authority. Refuted.** They are a closed rendering vocabulary. `bot_registry_projection.py` and the panel services consume durable state and derive views without writes.
6. **Candidate: `account_truth.py`, `account_safety.py`, `account_epoch.py`, or `live_portfolio.py` writes duty/deploy state because each contains lifecycle or retirement terms. Refuted.** Account Truth reads binding state; safety and epoch write separate permission/proof evidence; portfolio writes order/custody evidence. None calls a classified state mutator.
7. **Candidate: a host-daemon retirement proposal is a competing `RETIRED` decision. Refuted.** The daemon appends a typed `retirement_proposal`; only the Clerk fold turns a still-current proposal into a binding decision. Superseded proposals remain non-decisions.
8. **Candidate: SQLite `bot_config` and runner `strategy_instance.json` are concurrent writers to the same artifact. Refuted.** They are distinct stores with overlapping semantics, so there is no same-file write race. The surviving concern is cross-store partial commit and semantic divergence, not byte corruption.
9. **Candidate: all account binding writes bypass the Clerk. Refuted.** Normal daemon `DEPLOYED`/`ACTIVE`/`RETIRED` decisions go through a host-capability- and generation-checked Clerk RPC. The exceptions are explicitly named compatibility, retirement, and maintenance seams.
10. **Candidate: a read of fleet, panel, reconciliation, or deploy-preflight state can silently heal the durable phase. Refuted.** The inspected GET/projection paths are side-effect free with respect to the classified artifacts. Durable changes occur only on command, recovery, maintenance, or scheduled writer paths.

## Confidence and remaining uncertainty

- **High confidence — same-artifact writers.** The repository mutator calls, their constructors/factories, and the storage implementations were traced in both directions. The table distinguishes direct mutation from delegation.
- **High confidence — fencing.** The operation flock, individual artifact flocks, account binding ledger lock, SQLite generation/revision/lease fences, and lack of TTL/generation on the file-backed paths are explicit in source.
- **High confidence — projections/readers named by the issue.** Each named router, schema/vocabulary, admission, daemon-client, account evidence, and panel module was inspected for durable calls rather than classified from its filename.
- **Medium confidence — one numeric answer for “deploy writers.”** The phrase is not a defined domain term at this commit. Counting storage seams yields four deploy artifact families; counting command/policy entry points yields more. This audit reports both instead of manufacturing a single total.
- **Not determined from static code — deployed runtime topology outside the supported configuration.** A second process can only exploit an unfenced JSON writer if it shares the artifact root and invokes that path. The census identifies capability and fencing; it does not claim such a second process is currently running.

## Bottom line for the follow-on decision

The later authority ticket should not begin from “make the evaluator single writer” without first choosing which state machine is being unified. Duty phase/intent has a concrete implementation-vs-ADR mismatch. Alpaca deploy has deliberately separate custody and process evidence that needs a cross-store publication/recovery decision, not necessarily one physical database. The deprecated host/account-binding family is a migration/removal question and must not become the template for new Alpaca control work.
