# Simulated execution causality and live cost assumptions

Investigation: [[Codex] Simulated execution causality and live cost assumptions](https://github.com/tim1016/learn-ai/issues/2433). Baseline `10b5f31b529c8507bd19bb24015f3d85fa9aba43`; branch `research/codex-2433-fills`.

**Result: no new Critical/High.** One Medium control/contract mismatch, plus important model limits that must not be mistaken for newly discovered arithmetic defects. The configured fill models are deliberately different experiments; matching a LEAN log is not a claim to reproduce Alpaca fills.

## X1 — The paired-run commission control remains editable although the profile overrides it

**Claim.** Strategy Lab offers “Commission / order” for a Compatibility pair, sends its edited value, and accepts it, while the resolved engine charges the pinned IBKR fee model instead.

**Goal.** Trading intelligence; correctness.

**Severity. Medium.** The control is misleading and a user cannot vary this cost through it in paired mode. The explicit compatibility profile itself correctly names the fixed fee contract, actual total fees are returned, and no wrong implementation of that declared model was found. This is a bounded configuration-presentation defect, not an allegation that IBKR's reference fee model should become Alpaca's live model or that a falsely passing strategy was established.

**Evidence — proven and reproduced.** [The UI](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/Frontend/src/app/components/strategy-lab/strategy-lab-config-rail/strategy-lab-config-rail.component.html#L85-L109) hides the editable commission only for LEAN alone, so it remains for `both`. [The caller](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/Frontend/src/app/components/strategy-lab/strategy-lab-runner.service.ts#L289-L307) sends that value alongside the fixed profile. [Request validation](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/schemas/engine_backtest.py#L289-L306) rejects other incompatible execution knobs but accepts any nonnegative flat commission. [Engine construction](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/services/engine_backtest_service.py#L350-L373) then uses `IbkrEquityCommissionModel` and ignores the flat fee. [History persistence](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/services/engine_backtest_service.py#L1101-L1114) passes along the submitted flat value as well as the explicit profile; this is not a claim that stored total fees are recalculated from the wrong value.

The [offline characterization](https://github.com/tim1016/learn-ai/blob/research/codex-2433-fills/review/codex_2433_costs.py) validates a real paired request with `commission_per_order=99`, constructs its actual engine, and asks its fill model for the cost of 100 shares at 100: **1**, while an ordinary request constructed with the same flat setting produces **99**. The paired request still serializes 99. No data provider, persistence or engine job is invoked. The test isolates the configuration boundary, not a whole backtest or browser event.

**Why it matters.** A researcher can think a cost sensitivity changed when it did not. The explicit profile and observable total fees bound the error and make it detectable.

**Recommendation.** Present resolved execution policy in one place. In paired mode, disable incompatible flat commission input and show the pinned model; at the request boundary reject contradictory settings or clearly return which requested fields were overridden. Preserve the exact parity contract. Offer cost sensitivity only in a mode that actually applies it.

**Confidence. High** in the accepted request and constructed fee; **medium** in UI interpretation. A visible explanation tied to the paired control or a transformed resolved configuration would mitigate it. No owner decision is needed to make an existing fixed model truthful in the interface.

## Model choices, causal controls and limits

| Boundary | Evidence and conclusion |
| --- | --- |
| Signal-close versus deferred fill | [FillModel](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/engine/execution/fill_model.py#L1-L30) explicitly uses signal-bar close to reproduce the reference trade log; next-bar-open is a different experiment. [The main loop](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/engine/engine.py#L337-L450) processes already-deferred orders before delivering the new bar and queues newly generated deferred orders for a later iteration. Existing end-to-end synthetic stream tests verify those orders do not fill on the minute whose end caused their signal. |
| Gap behavior | The compatibility profile opts into the explicit stale-signal/current-open rule; ordinary signal-close retains its historical contract. Existing tests distinguish same boundary, overnight gap and next-session delay. This is a disclosed model difference, not proof of live executable arrival prices. The selected UI exposes signal-close/next-open; `NEXT_SESSION_OPEN` is a reference-fixture mode, not an additional selectable API mode. |
| Slippage and costs | [FillModel](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/engine/execution/fill_model.py#L145-L165) applies per-share slippage adversely by order direction and charges one canonical fee seam. Existing tests verify buy/sell direction, flat/model fees and configuration propagation. Grid/WFS [cell construction](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/research/grid_search/engine_adapter.py#L31-L48) forwards the saved cost settings. Zero slippage models no spread, market impact or queue/latency distribution; none is implied by a zero-cost run. No current fee schedule or exchange fee rate was recertified here. |
| Sizing scope | [SimpleFloorSizing and LeanSetHoldingsSizing](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/engine/execution/sizing.py#L1-L31) explicitly distinguish unbuffered research sizing from the narrow long-only reference port. The golden fixture reproduces 20 integer quantities with zero tolerance; fee-aware budget tests passed. Neither model claims a full buying-power/partial-fill/reservation simulation. The live Alpaca cash-envelope findings are separate and not explained away by this model limitation. |
| Signal versus execution feedback | The registered [signal-program tests](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/tests/engine/strategy/test_signal_program_exit_and_fill_semantics.py#L409-L512) cover exit reproposal eligibility and fill-callback isolation. They passed on synthetic streams. They do not guarantee that actual broker fill timing or rejected quantity equals a backtest. |
| Intrabar/limit features | The engine has resting-limit and pessimistic-bracket primitives. The inspected registered strategy/spec implementation contains no call to `submit_limit_order` or bracket-price attachment. Consequently this pass does not promote a suspected same-minute limit/gap-bracket issue into a product finding from custom test-only strategies. Activation by a real scoped registration would require a separate causal contract check. No arbitrary Research-product strategy path was pulled into scope. |

**Rationale retained.** [ExecutionConfig](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/engine/execution/execution_config.py#L35-L39) preserves “bit-exact LEAN parity” by default. [The sizing reference](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/docs/references/lean-set-holdings.md#L8-L14) deliberately declines to port LEAN's full buying-power universe because “porting them now would be bloat.” A narrow equivalence experiment does not need a universal exchange simulator. Those reasons remain valid; no silent change of golden/reference semantics is recommended. Separate any future execution-realism experiment from the versioned parity contract and state its assumptions. The owner-fixed IBKR-data/Alpaca-orders boundary is untouched.
