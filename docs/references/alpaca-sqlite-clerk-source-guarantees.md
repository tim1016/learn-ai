# Alpaca order-source guarantees and Clerk policy

**Reviewed:** 2026-08-06 against official Alpaca Trading API documentation.

This matrix separates a broker-documented guarantee from the stronger behavior the
Clerk must enforce. The current scope does not implement order replacement/PATCH.

| Source fact | Official source | Clerk consequence | Implementation / evidence |
|---|---|---|---|
| `GET /v2/orders` defaults to 50 and caps `limit` at 500. `after` and `until` are exclusive timestamps. `after_order_id` and `before_order_id` are exclusive ID cursors; the ID cursors are mutually exclusive and cannot be combined with the timestamp filters. | [Get All Orders](https://docs.alpaca.markets/us/reference/getallorders-1) | A sweep cannot claim completeness merely because one page returned. Pagination must follow one valid cursor mode and refuse a clean verdict if completeness cannot be proven. | `app/broker/alpaca/clerk/sqlite/reconciliation_sweep.py`; pagination and incomplete-sweep tests in the SQLite reconciliation suites. |
| A client order ID identifies an order and can retrieve it through `GET /v2/orders:by_client_order_id`. Alpaca documents client IDs as unique tracking identities and rejects duplicate submissions carrying the same ID. | [Working with orders](https://docs.alpaca.markets/us/docs/working-with-orders), [Get Order by Client Order ID](https://docs.alpaca.markets/us/reference/getorderbyclientorderid), [Trading CLI idempotent orders](https://docs.alpaca.markets/us/docs/alpacas-cli) | The Clerk commits a unique `client_order_id` before contact and uses exact lookup after response loss. An HTTP timeout is `UNKNOWN`, never fabricated failure or permission to mint a new economic intent. Local content-addressed constraints remain the primary retry guard. | `sqlite/enter.py`, `sqlite/exit.py`, `sqlite/uncertainty.py`; lost-response, duplicate, and restart tests. |
| A successful replace response does not prove the old order was replaced; a fill can race and cause the new order to be rejected later. While replacement is pending, buying power is reduced by the larger of old and new orders. | [Replace Order by ID](https://docs.alpaca.markets/us/v1.4.2/reference/patchorderbyorderid-1) | Any future PATCH operation must remain nonterminal until stream/REST evidence proves the terminal relationship and must reserve for the larger buying-power demand. Original fills remain real exposure. | **Not implemented / non-goal in #1395.** The Clerk exposes no PATCH path, so no code may infer these semantics from an HTTP 200. |
| DNR means “Do Not Reduce” for corporate-action price/quantity adjustment. Alpaca says ordinary non-marketable GTC limits can be adjusted and ordinary DNR opt-out is unsupported; bracket legs are sent with DNR/DNC. | [Placing Orders — bracket and time-in-force rules](https://docs.alpaca.markets/us/docs/orders-at-alpaca) | DNR is not the Clerk's internal `REDUCE` capability. `REDUCE` requires fresh, versioned proof that a proposed effect cannot increase attributed exposure. Never translate it into a broker DNR flag. | `sqlite/uncertainty.py::Capability.REDUCE`, `sqlite/exit_resolution.py`, `sqlite/recovery_policy.py`, and risk-reduction tests. |
| Order state is asynchronous: working states include `pending_cancel` and `pending_replace`; terminal status must come from later order/stream evidence. A cancel request can be rejected once no longer cancelable. | [Placing Orders — order lifecycle](https://docs.alpaca.markets/us/docs/orders-at-alpaca), [Delete Order by ID](https://docs.alpaca.markets/us/v1.4.2/reference/deleteorderbyorderid-1) | HTTP acceptance is not terminal custody evidence. EXIT cancels first, folds intervening fills, proves terminal siblings, and only then computes the remaining reduction from Clerk-attributed quantity. | `sqlite/exit.py`, `sqlite/exit_resolution.py`; partial-fill/cancel and lost-cancel-response tests. |

Official documentation describes broker behavior, not atomicity across this process and
Alpaca. Capture-before-contact, content-addressed command/effect identity, monotonic
evidence, append-mirror finalization, and fail-closed recovery are Clerk guarantees and
are validated separately in
`docs/references/alpaca-sqlite-clerk-invariant-traceability.md`.
