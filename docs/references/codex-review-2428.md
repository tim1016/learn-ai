## E1 — Contradictory broker execution cost can leave clean reconciliation and complete economic evidence

**Claim.** After exact executions establish an order's quantity and gross cost, a fresher broker order aggregate with the same quantity but a materially different average fill price is ignored economically. The system continues to publish the old fill basis and P&L with complete execution coverage, and account reconciliation returns clean when quantities agree.

**Goal.** Economic authority must preserve exact execution identity without silently overlooking contradictory current evidence. If a broker aggregate cannot identify a legitimate correction, the safe answer is unresolved economics rather than inventing a correction or certifying the old answer.

**Severity. High.** This is an undetected class of execution-cost disagreement capable of producing incorrect P&L and transaction evidence. The reproduction establishes a supported aggregate input with inconsistent economics and a clean result. It does not establish how frequently the current Trading API produces such restatements, that any real account was affected, or that the aggregate should automatically override the original exact fill. Those limits keep the finding below Critical.

**Evidence.**

1. **Reproduced through both fold and account reconciliation:** the isolated probe records an exact BUY of 10 GOOGL at 100, then an aggregate with the same economics, then a later `updated_at_ms` aggregate for the same order showing 10 at 90. It supplies a broker position of 10 with basis 900 and drives real `reconcile_account` through fake read/trade ports. Reconciliation returns `clean`. The real economic reader still returns exposure 10, open P&L 100 at mark 110, `marks_complete=True` and `execution_coverage='complete'`. The newer supplied basis would imply open P&L 200, but no correction identity was supplied: the necessary conclusion is **conflict**, not automatic acceptance of 200. The invariant requiring incomplete/unavailable economic evidence fails. [Pinned reproduction](https://github.com/tim1016/learn-ai/blob/11a51b70f823052e60f5925f88420bfb996c8c50/research/codex-2428/test_economic_evidence.py#L24-L81).
2. **Proven input asymmetry:** [aggregate ingestion](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/order_evidence.py#L228-L275) checks only a positive quantity delta before appending fill evidence. Same-quantity price changes take the acknowledgement path. [Acknowledgement facts](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/order_evidence.py#L400-L451) retain reported filled quantity but not average price/gross cost, so the contradiction is not retained there for a later economic comparison.
3. **Proven outer check limitation:** the active [account reconciliation orchestration](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/reconcile.py#L1008-L1048) folds snapshots and recovers operations before computing residual safety. Its [position agreement](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/reconcile.py#L216-L283) compares quantities, not execution cost. The reproduction confirms this outer check does not rescue the price-only case. Its position basis is corroborating evidence in a single-order fixture; the recommendation does not equate broker account average cost with strategy FIFO across arbitrary multi-bot activity.
4. **Proven confidence propagation:** [economic coverage](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/economic_projection.py#L1224-L1250) is incomplete for cumulative rows or an execution-coverage uncertainty. Neither exists in this case. [The snapshot](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/economic_projection.py#L800-L853) computes P&L from stored effective fills and carries that coverage. The panel's [coherence check](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/services/broker_v2_panel/sqlite_panel_adapter.py#L746-L758) checks authority/revision agreement, which cannot detect a contradiction discarded at ingestion. A browser rendering demonstration was not run.

**Why it matters.** Exact-fill authority is meant to prevent double-counting and arbitrary rewrites. It does not prove that a later contradictory order total is harmless. Here, exact ledger rows can remain internally self-consistent while external economic evidence disagrees; the internal checks and clean account verdict then lend confidence to an unresolved answer. This concerns the cost basis of an execution, independently of the earlier daily-loss time-basis or cash-observation findings.

**Recorded policy and counterargument.** The [cumulative fold rationale](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/folds.py#L1306-L1314) says, “out-of-order evidence never double-counts or reverses exposure,” and requires a named superseding execution for corrections. That is sound and is not being reversed. However, the probe's later source time and materially changed cost cannot be distinguished from a price restatement merely by finding no positive quantity delta. Ignoring the change is stronger than refusing to overwrite it. The [execution authority PRD](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/docs/prds/2026-08-10-sqlite-sole-authority-alpaca-execution.md#L213-L217) already requires an unexplained regression to raise uncertainty rather than silently write. Extending that conflict discipline to order gross cost satisfies the existing decision; no new owner choice is required to recognize a contradiction.

**Recommendation.** Preserve governing aggregate quantity **and gross cost/average-price evidence**, including its source time and identity. Compare it with effective exact economics under explicit quantity and vendor-price precision tolerances. Proven old snapshots remain non-regressing observations; material current contradictions raise durable economic uncertainty and prevent a complete economic claim until resolved. Apply a correction only after an explicit supersession proof; never rewrite exact fills from an unidentifiable aggregate. Make correction support and any unavailable provider evidence explicit. Do not broaden broker account cost-basis comparison into an assumed bot-level FIFO authority.

**Confidence. High** in the source path and synthetic clean verdict, **medium** in real-provider occurrence and recovery latency. Confidence in impact would change with a verified Trading API guarantee that average fill price can never change without an earlier processable exact correction, or another active consumer that fences these same aggregate inputs before all readers. No such path was found in the inspected application flow.

## Counter-evidence, corrections and unsupported events

- **Quantity disagreement has an outer safeguard.** The companion probe changes the latest total to 8 at 100. Stored exact economics remain 10, but `reconcile_account` returns `position_drift`. Its economic coverage still describes the exact rows as complete; the account warning is visible. This is explicitly not counted as another silent failure. The matching 10-at-100 control reconciles cleanly.
- **Exact corrections have meaningful durable semantics.** The [repository correction boundary](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/repository.py#L867-L943) validates ownership and the effective target or records uncertainty. The [fold](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/folds.py#L1180-L1263) retains superseded evidence and applies the quantity difference. [Economic lineage](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/economic_projection.py#L81-L115) uses the root execution time, so a late correction does not move a closing lot into the arrival day. Selected correction/FIFO/replay tests passed.
- **Duplicate exact evidence is not blindly trusted.** [Exact admission](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/repository.py#L549-L605) compares an existing effective identity's economics and raises coverage conflict for changes; restart dedup and cumulative-to-exact supersession controls passed. This protection does not perform E1's comparison against a same-quantity aggregate.
- **Do not confuse correction-capable storage with a supported provider protocol.** Searching application call sites found the correction API definition, but no application producer invoking it. The [active websocket sink](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/trade_evidence.py#L196-L240) produces exact fill slices plus aggregate acknowledgements. The [adapter](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/adapter.py#L373-L397) does not recognize `trade_correct` or `trade_bust`; the two new adapter controls prove they raise `ValueError`, rather than silently applying their economics. [Mapping errors](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/trade_updates.py#L568-L598) degrade execution-evidence health. The [correction validator](https://github.com/tim1016/learn-ai/blob/10b5f31b529c8507bd19bb24015f3d85fa9aba43/PythonDataService/app/broker/alpaca/clerk/sqlite/facts.py#L1159-L1182) also requires positive corrected quantity; it is not a zero-quantity bust model.
- **Provider-doc boundary:** the current [Trading API websocket documentation](https://docs.alpaca.markets/us/docs/websocket-streaming) lists the adapter's common/less-common lifecycle events; it does not establish that named bust/correction events are delivered on this stream. Alpaca separately documents them for [Broker API Trade Events SSE](https://docs.alpaca.markets/us/reference/subscribetotradev2sse). Both were read as public documentation on 2026-09-24; no endpoint was called. This investigation does **not** assume those APIs are interchangeable or claim an observed unsupported live event. Full bust/correction support remains unproven, not a second automatically Critical finding.

## Remaining boundary

No new owner decision is necessary for E1's conflict recognition: preserve immutable exact authority and disclose unprovable economics, as the existing design intends. A separate bounded technical investigation could establish the current retail Trading API's actual supported correction/bust acquisition protocol, replay guarantees and identity mapping, using official documentation or vendor clarification; Broker API SSE must not be assumed usable by this product. Only if multiple supported policies remain should the owner choose one.

Further unexamined cases are cross-order replacement chains, fee revisions after an execution correction, per-bot allocation of account-level charges, and process/power loss at every write boundary. No frontend/.NET execution tests, real-provider transport tests or live/paper-state inspection were performed. The report and reproduction are recommendations/evidence only; no source fixes or PR were created.
