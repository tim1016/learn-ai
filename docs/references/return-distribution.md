# Daily return distribution study

**Concept**: Take the minute bars a symbol already has in the data lake, compute each trading day's return three ways (close-to-close, session-only, overnight gap), and histogram the days into fixed-width "baskets" — the empirical distribution of daily returns, the study shape of Fama (1965) §I.B and Mandelbrot (1963). Clicking a basket opens the days inside it, each decomposed across the full 24-hour cycle (overnight gap, pre-market, morning, afternoon, after-hours), plus a minute-candle view of the selected day.

**Canonical implementation**: `PythonDataService/app/research/return_distribution.py` (all math, pure functions over bars + factor rows), `app/services/return_distribution_service.py` (lake read + orchestration, off the event loop per #1943), `app/routers/return_distribution.py` (`POST /api/research/return-distribution`). Engine row in `docs/architecture/engine-authority-map.md`.

## Corporate-action adjustment

The study reads the **raw** lake root (deepest coverage) and multiplies each day's anchors by the lake's own LEAN factor-file `price_factor · split_factor` as of that date. Parsing and the as-of lookup are canonical in `app/data_lake/factor_files.py::factor_multiplier_as_of`, which implements LEAN's `CorporateFactorProvider.GetScalingFactors` semantics: the **earliest row dated on or after** the bar wins (a row dated D covers data back through D; D's successor uses the next row; data before the first row uses the first row's cumulative factors; data after the last row is unadjusted). Splits and dividends are therefore both removed from the return series, with event-day continuity parity-tested against a verbatim port of LEAN's walk.

The adjustment is always split-and-dividend on the latest-known basis (owner decision #2432), and it is only applied where the factor file provably covers it (#2452). The lake builds a symbol's factor file over **every captured session**, never over one request's window, and writes a coverage record beside it (`<symbol>.coverage.json`: the covered spans — maximal runs of captured scheduled sessions — as int64 ms UTC session-open anchors, bound to the CSV's SHA-256). The study reads it only through `factor_files.read_covering_factor_rows`, the single coverage check: each run of scheduled-adjacent sessions it adjusts must lie inside one covered span. Inside a span every action with `first < ex-date <= last` is present and priced on the prior session's close, so every in-span ratio is exact; an action outside every span scales a whole span uniformly and cancels (the one inherited exception — the builder's dividend formula multiplies the cash by the later splits' cumulative factor, which QuantConnect's own factor files do not — is pinned and documented in `tests/data_lake/test_factor_files_coverage.py` as an open question). A reference session whose close cannot be read (extended-hours bars only, or an unreadable zip) ends its span there, so its action falls outside every span and only windows crossing that session are refused — not the whole symbol. Adjusted *levels* are on the basis of the last covered session, not today's, so nothing on this page presents one. A file with no record, an unreadable record, or a record bound to other bytes covers nothing. An uncovered window triggers the on-demand capture (which rebuilds the file); if it is still uncovered, the study is refused with a typed `ADJUSTMENT_NOT_COVERED` 409 naming the uncovered sessions and what the capture did — never answered with returns labelled adjusted that are not. Lake prices are deci-cent quantized (1e-4 grid), the same precision seam the chart documents; at 0.5% bin width this is four orders below decision-relevant scale.

## Coverage semantics

The service reads a 14-calendar-day lead-in before `from_date` so the window's first session has a previous close to return against; the on-demand probe checks that lead-in too, so a lake holding the requested dates but not the fortnight before them is still captured. The capture boundary splits sessions under the **extended** policy — this study consumes after-hours bars, so a session only counts as immutable capture history once its 20:00-ET tape has finished. Error mapping keeps caller errors and operational failures apart: unusable study geometry (including a bin count beyond 100 per side) is a typed 400/422, while a malformed factor file or corrupt lake zip propagates as an operational 500 rather than masquerading as an invalid request. `coverage` reports requested (scheduled) vs returned sessions, missing sessions (scheduled but not captured even after the on-demand capture), and excluded sessions (captured but without RTH bars); days whose previous scheduled session is missing keep `null` close-to-close/overnight with a warning rather than spanning the gap. Fewer than 30 captured sessions is a typed `INSUFFICIENT_COVERAGE` 400. First-time captures of a two-year window can take tens of seconds; the frontend loading state says so.
